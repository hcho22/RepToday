US-E05 (`Services/Engine/AdaptiveOverload.swift`) tunes Step 6's per-cycle bump curve into the **Asymmetric Ramp** - back off fast, climb slow: a single recent `too_hard` or a **skip** of the exercise pulls the next target down eagerly (`hardStep` steepened to `0.80`, a 20% back-off), while `too_easy` climbs only patiently (`easyStep` gentled to `1.10`, a 10% rise) and `justRight`/unrated nudges up by the gentlest `progressiveStep` (`1.05`), so the down-step magnitude is always >= the up-step (`(1 - hardStep) >= (easyStep - 1)`, asserted on the constants) and every signal still moves by at least one so direction is never lost to rounding. The `too_hard`/`too_easy` mapping plus the new skip signal are resolved into a private `RampSignal` (`eased`/`intensify`/`progress`): `demonstratedCapacity` now scans past a skipped most-recent entry to read the set count and per-set value from the earlier worked session but remembers the skip and forces `.eased`, so a recent bail eases the target (below capacity) even over an earlier `too_easy`, without the skip becoming the capacity *source*. The ramp composes with US-E03's `progressionRate` unchanged - the rate still paces only the two advancing steps, never the eager down-step - and stays within the existing rep/hold/set rails.

The Return itself carries no readjustment; the readjustment lives in the Re-entry Ramp: `sessionPolicy.reentry.rampSessionsRemaining` (seeded to `rampSessions` = 3 by the Programmer after a Return, US-F03) drives `ReturnOverride.rampScale`, which walks the volume scale from that floor back to neutral `1.0` as the counter decrements, so `AdaptiveOverload.target` (now taking a `reentryScale:` - neutral `1.0` by default, applied only to capacity-derived per-set targets, and always landing at least one below the un-held target down to the rep/hold rails) holds difficulty below normal on the sessions after a Return and climbs it back. The Return decision is made once (the shared `SessionAssembly.isReturnSession`, gating both the overrides and the flag) and stamped on the assembled `Workout.wasReturn`, so the post-session log-writer (US-L01) records it onto `WorkoutLog.wasReturn` (US-D02) rather than re-deriving detection at a different `asOf`. Every override is a pure function of its inputs and a no-op in the steady state, so a present, warmed-up user runs exactly the US-E03 pipeline; with US-E06 done the Epic E engine extensions are complete, and Epic F (the AI Programmer that writes the policy, including seeding the `reentry` ramp on a `return` trigger) is next.
The v6 Epic F AI Programmer has begun: US-F01 (`Services/Programmer/ReprogramTriggerDetection.swift`) opens the on-device, deterministic Programmer with **re-program trigger detection and Trigger Precedence** - the detection half of the seam whose re-weighting lands in US-F02/US-F03. `ReprogramTriggerDetection.dueTriggers(user:recentLogs:library:asOf:calendar:)` is a pure function returning the due `ReprogramTrigger`s (US-D04) in precedence order, so the client can re-program on open against the highest-precedence one without any server clock and the new policy applies one open later. It detects the four PRD kinds: `weekly_boundary` (the injected calendar's `weekOfYear` for `asOf` is strictly later than the most recent log's week, so a just-closed Consistency-Score week exists to re-tune against - never for a no-history user), `return` (reuses `ReturnOverride.isReturn`, the single Return-detection seam so the Programmer and engine can never disagree on what a Return is), `physical_stall` (for each chain the user has worked, the frontier tier - the highest-order worked tier, the same notion Step 5 uses - has an existing next tier (`progressionId != nil`) yet its parsed `AdvancementCriteria` are cleared in `stallClearedSessions` = 2+ distinct sessions while the frontier never rises, meaning that real next tier is gated and the user is genuinely stuck; a single-tier or top-of-chain movement has nothing to advance to and never stalls, so the library's easily-met single-tier mobility chains never misread a healthy user as a plateau), and `disengagement` (over the most recent `disengagementWindow` = 3 completed sessions, the per-session completion ratio `durationMinutes / requestedMinutes` - clamped to 1 - forms a declining non-increasing run whose newest value falls to <= `disengagementCompletionRatio` = 0.6, or a window skip rate >= `disengagementSkipRate` = 0.5; reading the requested-vs-completed gap rather than absolute completed minutes is deliberate per US-D02, so a user who intentionally requests shorter sessions and finishes them - Default Duration learning - is never misread as pulling away, and lengthening gaps are already the Return trigger). **Trigger Precedence** is enforced at the source - when both apply, `disengagement` suppresses `physical_stall` so a user pulling away is never handed more challenge - and the returned order (`return` < `disengagement` < `physical_stall` < `weekly_boundary`) mirrors it. Detection is pure and deterministic over `(user, recentLogs, library, asOf)` - the clock is injected as `asOf` and stamped onto each trigger's `detectedAt`, never read from the wall clock - and needs the validated `library` only to resolve advancement criteria and chain position for the stall signal; the concrete `SessionPolicyServiceProtocol` (US-F03) supplies the library and adapts this to the protocol's library-free `dueTriggers(user:recentLogs:asOf:)` (the shell `MockSessionPolicyService` still reports no triggers until then).
US-F02 (`Services/Programmer/PlateauDiagnosis.swift`) adds the Programmer's **plateau diagnosis** - telling a *physical stall* (capacity earned but gated) apart from *disengagement* (pulling away) and mapping each to the Session Policy levers US-F03 writes.
The two plateau predicates that US-F01 detected inline (`isPhysicallyStalled(recentLogs:library:)` and `isDisengaging(recentLogs:)`, with their tuning constants `stallClearedSessions`/`disengagementWindow`/`disengagementCompletionRatio`/`disengagementSkipRate`) now live here as the single seam, and `ReprogramTriggerDetection.dueTriggers` composes them rather than re-deriving them - so detection and diagnosis can never disagree about what a stall or a disengagement is (the same pattern by which US-F01 reuses `ReturnOverride.isReturn`), a behavior-preserving move that leaves US-F01's trigger output unchanged.
`PlateauDiagnosis.diagnose(recentLogs:library:) -> Plateau?` returns the single plateau in force (`.physicalStall`/`.disengagement`) or `nil`, applying the same Trigger Precedence at the source (disengagement wins, so a diagnosis can never hand more challenge to a user pulling away); it is pure over `(recentLogs, library)`, reading only log history (the completion ratio and skip rate are the consistency signals, straight off the logs per US-D02) with no clock, and needs the `library` only to resolve advancement criteria and chain position for the stall.
The **explicit lever mapping** `PlateauDiagnosis.reweighted(_:for:)` moves only the affected levers on a passed-in policy and leaves `version`/`updatedBy`/`note`/persistence to US-F03: a `.physicalStall` multiplies `progressionRate` by `stallProgressionBoost` (1.15) and widens `varietyWindow` by `stallVarietyWiden` (+1) for a capable-but-gated user, while a `.disengagement` eases `progressionRate` by `disengagementProgressionEase` (0.85) and narrows `varietyWindow` by `disengagementVarietyNarrow` (-1) - lower difficulty, less novelty - and never raises challenge; both are clamped to the rails (`minProgressionRate`/`maxProgressionRate` 0.5...2.0, `minVarietyWindow`/`maxVarietyWindow` 1...6) so recurring plateaus accelerate or ease without running away.
The session-length half of "less friction" for disengagement is delivered by Default Duration learning (US-F04) - the policy carries no session-length lever, so the mapping does not fabricate one.
US-F04 (`Services/Programmer/DefaultDurationLearning.swift`, `Services/Programmer/PolicyNote.swift`) adds the Programmer's two honesty pieces - both pure, deterministic, and left to be wired by the re-weighting service (US-F03), the same way US-F01/US-F02 provide pure logic no service yet calls.
`DefaultDurationLearning.learned(_:completing:)` (and its `from recentLogs:` convenience) folds newly-completed session `durationMinutes` - what the user *finishes*, never what they *request* (US-D02) - into `User.Duration.completedDurationEWMA` (a `smoothingFactor` 0.3 EWMA whose prior is the existing average, else `onboardingSeedMinutes`, so learning is anchored to the stated preference until real evidence accrues), then sets `defaultMinutes = snappedToChip(ewma)` against the ascending `chipValues` (5/10/15/20/30/45/60), a boundary snapping to the shorter/gentler chip; `onboardingSeedMinutes` is never mutated and empty input is a no-op, so a user requesting 20 but completing ~12 drifts the default to 10/15 while the caller (US-F03) avoids double-counting by folding each session once.
`PolicyNote.templated(policyBefore:policyAfter:durationChange:)` builds the user-visible `SessionPolicy.Note` (always `source == .template`) from the **real diff** - the direction `progressionRate`/`varietyWindow` actually moved plus any Default Duration change - never from the trigger's intent: it names a stepped-up challenge / eased intensity and fresher / familiar movement only when the levers moved that way, appends the new go-to duration only when it changed, returns `nil` when nothing observable changed (the honest outcome), and never invokes the user's `why` (no hollow motivation callback), so the note can only ever claim a change the sessions actually reflect.
US-F03 (`Services/Programmer/DeterministicSessionPolicyService.swift`, `Persistence/CoreDataSessionPolicyStore.swift`, `DI/ServiceContainer.swift`) completes Epic F with the real, persistence-backed re-weighting service that finally composes the Programmer's four pure pieces (US-F01 detection, US-F02 diagnosis + lever mapping, US-F04 Default Duration learning + templated note) into the `SessionPolicyServiceProtocol` the client will call on open.
`currentPolicy(for:)` reads the last-written policy from an injected `SessionPolicyStore` (or `SessionPolicy.default` until one exists), and `dueTriggers(user:recentLogs:asOf:)` adapts US-F01's library-taking detection to the protocol by supplying the validated catalog from the exercise service.
`reprogram(user:recentLogs:trigger:)` writes a fresh policy: it moves the optimization levers for the trigger (`physical_stall`/`disengagement` re-diagnose the freshest history through `PlateauDiagnosis.diagnose` and apply `reweighted`, so **Trigger Precedence holds end-to-end** - a stall trigger can never accelerate a now-disengaging user; `return` seeds `reentry.rampSessionsRemaining` to `ReturnOverride.rampSessions` = 3 and touches no optimization lever, discipline overriding optimization; `weekly_boundary` moves no lever on its own), folds Default Duration learning over only the non-Return sessions completed after the current policy's `updatedAt` (the `updatedAt` cutoff is a dedup boundary so the EWMA folds each session exactly once across re-programs - `default`'s 2001 sentinel epoch folds the full first history - and `wasReturn` sessions are excluded because their deliberately short, capped duration (US-E06) would drag the learned default down and soft-penalize a celebrated comeback), stamps `version += 1` / `updatedBy == .deterministic` / `updatedAt = trigger.detectedAt` (time injected, never the wall clock), attaches `PolicyNote.templated(...)` built from the real before/after diff (so the note can only claim a change the sessions reflect, and is `nil` when nothing observable moved), and persists the learned `user.duration` first (via `UserServiceProtocol`, only when it moved, since policy and user are separate aggregates) then the policy (via the store), so the policy's `updatedAt` dedup boundary only advances after the duration derived from those sessions is durably saved. The service **never generates or returns a workout**; it only writes policy. Persistence is a `SessionPolicyStore` protocol with an `InMemorySessionPolicyStore` (tests/previews/the mock container) and a `CoreDataSessionPolicyStore` (the running app, backed by `CDSessionPolicy` so the policy survives relaunch and offline use, US-J02 will sync it); the real service is wired into `ServiceContainer.mock()` in place of `MockSessionPolicyService` (the one-line swap), returning the default until it has written a policy so pre-programming behavior and `ServiceContainerTests` are unchanged. With US-F03 done the Epic F AI Programmer is complete; the on-open *client invocation* of `dueTriggers`/`reprogram` lands with the Ready Screen (US-J02).

`ColdStartOverride.startBandedPool` bands the **strength and primal** pool to `[startingDifficultyFloor, cappedMaxDifficulty]` under the already-applied cap, so Step 5's lowest-eligible selection for a no-history user starts at the *band entry* rather than the chain's entry tier (an advanced user's first push is a difficulty-3 pike/diamond push-up, not a wall push-up). Mobility is never floored - the warm-up, Movement Practice, and cooldown all draw from it and a stretch's difficulty is not training load - so warm-up/mobility/cooldown are byte-for-byte identical at every level; and the band can never empty a movement pattern: the floor is clamped down per pattern to the hardest movement that pattern actually offers inside the cap.
The floor is tuned against the library a Discipline-Phase user can actually *reach*, not the nominal 1-5 scale: setting each level's floor equal to its own cap collapsed the "band" to a single tier and landed intermediate and advanced on the same movements, so the floor sits a tier beneath the cap instead, which keeps each band a real range and the two pools genuinely different (intermediate opens the whole 2-3 band, advanced only its top).
Sitting the floor beneath the cap was only half of it, because the reachable catalog itself was too short. `ExercisePoolFilter` gates `phase == .strength` out for every MVP user, and the shipped library put every gated skill at difficulty 5 with nothing Discipline-reachable above 3 - so the advanced `[3, 4]` band resolved to seven movements, and five of the six banded patterns offered exactly **one** progression chain inside it. Chains, not movements, are what the variety window rotates over: Step 5 resolves a pattern by picking one exercise per chain, so a single in-band chain hands the user the identical movement every session of the week however many tiers that chain carries. The answer was to extend the *reachable* range rather than weaken the band or unlock the Strength Phase early - earning that phase is a product principle, not a gate to route around. `Resources/Exercises.json` grew from 42 to 57 movements with fifteen zero-equipment Discipline tiers at difficulty 3-4 (archer push-up; cossack and shrimp squats; marching glute bridge and long-lever single-leg bridge; bear hold, hollow rock and tuck L-sit; a whole `pull_horizontal` chain of wall scapular pulls and supine floor rows; a `primal_ground_flow` chain of gorilla walk and lizard crawl; and, closing the last single-tier gap, an underswitch and a bear-hover shoulder tap so `locomotion` finally carries difficulty 4 too), slotted into existing chains where one continued and into new chains for the two patterns that had only one. Phase now gates *skills* rather than tiers - the three gated movements are the library's difficulty-5 summit, and every tier beneath a summit is reachable - and two standing gates hold the band open: `ExerciseLibraryTests.testAdvancedStartBandHasRoomToRotate` keeps at least two in-band *chains* per banded pattern, and `testEveryBandedPatternSpansTwoTiersInsideItsStartBand` at least two in-band *tiers*, so a `[floor, cap]` label can never sit on what is really a single difficulty.
The Zero-Equipment Floor is about the *room*, not just the kit, so four of those first thirteen were re-authored: a doorway row, two table rows and a Nordic curl negative all satisfied `equipment == []` on a technicality while quietly requiring a door frame, a table that would hold body weight inverted, or anchored ankles. They are replaced at the same difficulties by movements that need only a floor and a wall - a wall scapular pull, a supine floor row and its single-arm progression, and a long-lever single-leg bridge - so `apartmentFriendly: true` is a fact the library states rather than a flag a test had to certify.
Banding also left a cliff on the far side of the handoff, and that one is an engine flaw rather than a content gap.
A chain the band withholds is never prescribed, so it accrues no history; the session `ColdStartHandoff` clears the contract, its untouched entry tier is the only candidate the variety window has never seen, and freshness alone would hand an advanced user a difficulty-1 wall sit.
Three rounds of trying to fix it with a difficulty *floor* in Step 5 established that the approach was structurally wrong rather than merely mis-implemented: a floor is a lower bound, while the Return override, the `too_hard` de-escalation, and the skip escape hatch are all upper bounds, so putting them on the same dial produced a fresh collision every round - the floor inverted the Return cap, then permanently retired whole progression chains once a pattern reached difficulty 4, then anchored itself to an onboarding self-report nothing ever revises, then switched itself off on a routine skip.
The fix is to remove the conflict instead of refereeing it.
Freshness has exactly one blind spot - it cannot tell "the user outgrew this" from "the engine never let them see this" - so `ColdStartOverride.withheldByStartSeed` names the movements the band held out of reach and Step 5 stops counting those as new: `selectInChain` enters a no-history chain past them, and `select(pattern:)` sets them aside before consulting the variety window.
Nothing is filtered and nothing is forced, which is what makes the ceilings win for free rather than by precedence rule.
A Return caps the pool at difficulty 2, which leaves nothing in-band to prefer, so every candidate comes back into scope and the gentlest tier is served exactly as it was before the band existed - and the same is true of an injury filter or any other narrowing.
A `too_hard` session eases the seed itself, and the withheld set is resolved from that same eased seed, so the tier the seed just reopened stops being withheld in the same move.
A skip changes nothing here at all.
The withheld set is a factual claim about the user's own cold-start week rather than a policy dial, so it is recorded rather than re-derived.
While cold start is active it is the live seed; on the session that retires the band `ColdStartHandoff` writes the floor the week actually ran at - the seed as eased by every `too_hard` rating it produced - to a new additive `User.ColdStart.bandFloorAtHandoff`, and afterwards Step 5 reads exactly that.
Only that rating moves the tier: a skip is the product's escape hatch ("not this movement") and eases the seeded *volume* alone, mirroring the Asymmetric Ramp, so a routine tap cannot permanently erode a band that outlives the log window.
The contract's un-eased aim is recorded beside the floor as `bandAimAtHandoff`, because the retiring session's own rating is collected on the completion screen and therefore always lands after the handoff has run; `ColdStartHandoff.revisedBandFloor` re-resolves the recorded floor from that aim when it does, touching no counter, so an explicit `too_hard` on the fifth session still reaches the band the rest of the account is measured against.
Deriving it at selection time instead was the first attempt and it does not survive: the engine's `recentLogs` is a bounded 70-day window (`ReadyViewModel.recentLogLookbackDays`), so the cold-start sessions - and the `too_hard` rating that eased the floor - age out, after which a derivation quietly re-raises the tier the rating lowered and starts asserting a band the user never lived through.
The field decodes to `nil` when absent, which reads as "no banded cold start ever ran" and withholds nothing: correct for a record persisted before US-O02 (whose contract decodes its Start Seed to the neutral floor, so that week genuinely ran unbanded), for a contract carrying the neutral floor, and for any generation against `SessionPolicy.default`.
That closes the second half of the problem too - `coldStart.active == false` is equally true *before* a contract exists as after one retires, so gating on the flag alone had been asserting a band retroactively over users who never had one.
`StartSeedTests.testSessionAfterTheHandoffNeverRegressesBelowTheColdStartTiers` is the standing gate - it walks a full five-session cold start and asserts the sixth session regresses in no pattern, including one that week never trained.
`ColdStartOverride.volumeSeed` hands the volume half to Step 6: `AdaptiveOverload.target` gains `startingRepMultiplier`/`startingSets` parameters that scale **only the no-history default target** - the very first prescription of a movement, where there is no demonstrated capacity to be relative to - clamped to the existing `maxReps`/`maxHoldSeconds`/`maxSets` rails; a capacity-derived target (session 2+ of that movement) ignores the seed entirely, and the neutral values reproduce the pre-seed target precisely. `SessionAssembly` applies it only to the strength and primal blocks, matching the floor's scope.
The safety net for an over-reported level corrects the **tier**, not just the volume. The Asymmetric Ramp (US-E05) still eases reps eagerly on a `too_hard` rating or a skip, but on its own that would hold a user at an unwinnable tier for the whole five-session cold-start window, since the band removes every gentler tier from the pool. `ColdStartOverride.startSeed` therefore resolves the *whole* seed against `recentLogs`: it counts the same eager down-signals the ramp reacts to (a session rated `too_hard`, or one where the user bailed on a strength/primal movement) and steps the floor down a tier, drops a set, and eases the rep multiplier by the ramp's own `hardStep` per signal - never past neutral, and never touching a beginner's already-neutral seed. Tier and volume ease together on purpose: de-escalating onto an easier movement the user has never logged would otherwise re-apply the full volume seed to it.
The in-session swap (US-C08) now carries the seed across its seam: `WorkoutEngineProtocol.swapExercise` takes the `sessionPolicy`, which `ReadyViewModel` -> `ActiveSessionView` -> `ActiveSessionViewModel` thread through from the policy the session was generated against, so `ExerciseSwap` sizes a substitute with the same Step 6 levers (`progressionRate`, the Start Seed, `varietyWindow`) as the rest of the lineup instead of silently re-deriving it at the neutral seed. The default `SessionPolicy.default` argument reproduces the pre-policy swap exactly.
Finally, the seeded target is reflected in the **planned wall-clock**.
`Exercise.estimatedTimePerSetSeconds` is one constant calibrated against the movement's own default per-set value, so reading it directly assumed every set was prescribed at that default.
It is also not pure per-unit work: getting into position, bracing, switching sides and getting out again is paid once per set whether the set is 8 reps or 20, and in the catalog that fixed part is often the bulk of the estimate (`mobility_9090_hip` carries a 70s estimate on a 30s hold).
`SessionAssembly.workSecondsPerSet` therefore splits the estimate into a fixed per-set **setup** cost plus a **per-unit** cost.
Exactly one of the two halves has to be assumed and the other read off the movement's own authoring, and which way round matters.
A hold's per-unit cost is known a priori - one second of work per prescribed second, *per side* for an `isPerSide` movement, because a "20 second" side plank is 20 seconds left plus 20 seconds right - so its setup is the authored remainder `estimate - sides × defaultDurationSeconds`, which the catalog puts at 5-25s.
A rep has no authored duration to anchor that half, so for reps the *setup* is the assumed one (`setupSecondsPerSet`, capped by `maxSetupShareOfEstimate`) and the cadence is the authored remainder `(estimate - setup) / defaultReps`.
That is the right way round because cadence genuinely varies per movement - the catalog spans `hinge_glute_bridge` at 15 reps in 40s to `push_one_arm` at 3 in 50s - while getting down onto the floor and back up is much the same work whatever the movement is.
The first attempt had it backwards: it pinned the per-rep cadence at a global 3.0s and let the setup absorb the entire residual, which misclassified everything that genuinely scales with the target as a fixed cost and so *under*-charged per-side and slow-tempo movements, in places worse than the strict-proportional model it replaced (a `core_side_plank` grown to 40s was priced at 65s against 85s of real holding - a 60s under-count from a single slot over three sets, the whole ±1 minute budget).
That constant was also circular: it was calibrated from the four rep entries it then assigned zero setup to, asserting they have no setup at all.
`setupSecondsPerSet` is calibrated from a different family instead - the holds, where the setup is *observed* rather than fitted, and whose authored remainders have a median of exactly 10s.
Both halves reproduce the authored estimate exactly at the movement's own default, so a default-sized session is priced precisely as the catalog wrote it and only a moved target is re-priced - which keeps the ±1 minute timing promise honest for a x1.30 first session and for any capacity-grown one, without the strict-proportional model's systematic over-charging or the per-side-blind split's under-charging (a 40s `mobility_9090_hip` hold costs 90s; a 40s `core_side_plank` costs 85s; `push_archer` at 8 reps costs 74s rather than 59s; a hold clamped to `maxHoldSeconds` costs its setup plus the hold on every side, not a scaled estimate).
The per-side signal is a new additive `Exercise.isPerSide` rather than a parse of the user-facing `advancementCriteria` copy, so timing does not silently depend on wording; it is optional (absent means not per side) so an older `Exercises.json` and an already-persisted active session still decode, and a library test cross-checks the flag against that copy in both directions.
That cross-check originally matched a closed whitelist of per-side phrases, which meant an unfamiliar wording ("3x8 clean reps per arm", natural for the upper-body chains) simply fell through to "not per side" and the movement was silently under-timed by half - the exact failure the gate exists to catch.
It now asserts *positively* that every criteria string matches one of a small set of recognised authoring templates, with a second backstop that no criteria may name a limb at all outside a recognised per-side marker, so an unanticipated phrasing fails loudly instead of defaulting.
Making the per-side cost explicit also exposed two rails that were per-side-blind.
`AdaptiveOverload.maxHoldSeconds` is documented as a safety rail against an absurd prescription, but for a per-side hold it meant three minutes *per side* - a single set costing more than the entire budget of a 5-minute session - so `clampPerSet` now divides the ceiling by `sidesPerSet` and the rail means what its doc says for every movement.
That matters because the timing fit's only levers are set counts and item promotion/dropping: it can never shrink a per-set target, and warm-up, Movement Practice and cooldown all carry `minItems: 1`, so an unbounded per-side hold could push a short session past ±60s with nothing available to adjust.
The clamp does bound it - a fit case driving every per-side hold in the catalog to its rail now lands inside ±60s at all five durations, and fails without the clamp.
The existing ±1 minute tests could not have caught this: they run against history sitting near the movements' rep defaults with no holds at all, which is precisely the configuration where the split and the doubling are both no-ops.
Finally, the loop is closed in the player: `targetText` and `targetAccessibilityText` now read "3 × 0:30 per side" and "3 sets of 30 second holds per side", driven off `isPerSide` so the copy cannot drift from what the engine charges.
Previously the per-side instruction appeared only in `advancementCriteria`, which is progression copy rather than the prescription, so a user handed a 40s side plank who held it once did 85s less work per set than the session was planned around - over three sets the whole ±1 minute budget from one slot.
One point worth recording so it is not re-litigated: the work half of a session is never *timed*.
Nothing counts a rep or a hold down, the only countdown in the player is the rest timer, and a completed set logs the target it was prescribed rather than anything measured.
So this is a planning-only quantity whose single job is fitting a session to the minutes the user asked for; chasing per-second accuracy on a self-paced activity would be false precision.
What matters is that the model carries no *systematic* bias, because a consistent per-slot error accumulates where random error averages out - and that is exactly what both of the failed models had.
Because a strength block whose items already sit at `maxTrainingSets` has no "add a set" lever left (the advanced seed opened exactly there when the rail was 4, and a capacity-grown block still reaches it after the later 4 -> 5 raise), the fit lost that lever entirely, so reserve promotion now enumerates every set count within the rails rather than only the count Step 6 prescribed; without it a 10-minute advanced session parked 91s short of the request.
The seeded **set count** remains a pre-fit starting volume - the timing fit may still trade sets against the duration the user asked for, and the requested duration wins.
The swap's slot-budget check is measured through that same model.
It resolves the candidate's `OverloadTarget` first and prices **both** sides with `SessionAssembly.workSecondsPerSet` at the target each actually carries, so `slotToleranceSeconds` bounds the session's real wall-clock rather than two movements' default-sized estimates - previously a capacity-grown 20-rep `push_diamond` slot accepted a never-logged `push_pike` opening at its 8-rep default on a reported drift of zero while the session lost minutes.
Honouring the real budget on its own, though, did not merely narrow the candidate pool - it very nearly removed the feature.
A substitute the user has never logged always opens at its own default while the slot it replaces carries a grown target, and at a fixed set count the 30s tolerance leaves only ~10s of per-set headroom: sweeping the Discipline strength/primal catalog found an in-budget peer for 42/42 movements at the default target but only 18/42 at x1.5 of it and 3/42 at x2.0 - and x1.5 is ordinary, since `push_standard` opens at 8 reps and advances at "3x12".
The fix is the **set count**, the same lever the assembler's own timing fit uses, rather than a wider tolerance.
`ExerciseSwap` now picks the substitute's set count inside `minTrainingSets...maxTrainingSets`, comparing full slot seconds (`sets × workPerSet + (sets - 1) × rest`) so the rest a set change adds or removes is counted - rest being the one part of the budget that is exactly known.
The original count wins whenever it is already in budget, so a swap restructures a slot only when leaving it alone would push the session out of its stated minutes, and `.noAlternative` is reported only when no permitted count fits.
Making that promise actually true took a second pass: `bestFitSets` settles each candidate's *own* best count, and the selection then compared drift across all of them, so drift outranked set-preservation and slots were restructured gratuitously - `push_standard` grown to 10 reps returned `push_wall` at **4 sets** (drift 18) when `push_diamond` fit at the original 3 (drift 27), and with no growth at all `mobility_pigeon` returned `cat_cow` at **2 sets** when `mobility_9090_hip` fit at 1.
Catalog-wide that was 40 such cases at 3 sets/40s rest and 28 at 1 set/15s rest.
Set-preservation is now the *first* selection criterion, so drift is compared only among candidates that fit the slot as built and a re-picked candidate is reachable only when none does; both named cases now return the same-set peer, and the gratuitous count is 0 in each configuration.
The lever is scoped as the assembler scopes it: the warm-up and cooldown are built `allowSetAdjust: false`, so a bookend slot keeps its single set and simply declines instead - which required `ActiveSessionViewModel.snapshotForSwap()` to stop collapsing the lineup into one strength block and preserve the real block structure, since the block is what makes that distinction visible to the seam.
Because a bookend has no lever *and* no rest, a flat 30s gate there is the strictest test applied to the softest quantity, so a non-adjustable slot gets `slotToleranceSeconds + 0.3 × its estimated work` instead.
The 0.3 was read off the catalog rather than picked: at the time it was set, across all 57 movements the widest gap between a movement's own per-set work at its default and its nearest in-band peer's was 30% (`mobility_pigeon` at 100s against `mobility_9090_hip` at 70s; the 95th percentile 14%), so the band was exactly wide enough to admit every pair the catalog then authored as equivalent and no wider, and it is additive so a very small slot keeps the flat allowance rather than a tighter one.
The later one-set Movement Practice mobility expansion (see below) only narrowed those gaps - `mobility_lizard_lunge` at 90s now sits between pigeon and 90/90, so the former 30% outlier pair is closer - leaving 0.3 a safe (now slightly conservative) upper bound rather than a tight fit; the whole-library swap coverage sweep, unchanged in method, confirms it still admits every authored-equivalent pair over the expanded 71-movement catalog.
Measured over the sweep in the **adjustable** 3-set/40s-rest shape, coverage recovers to 42/42, 38/42, 41/42 and 38/42 at x1.0/x1.25/x1.5/x2.0 of the Discipline strength/primal catalog, and the flat 30s tolerance is unchanged there.
That shape is the one where the set lever always exists, so it is now measured alongside the real bookend shape (1 set, `mobilityRestSeconds`, non-adjustable), where the mobility movements cover the whole catalog at every growth level bar the single hardest (26/26, 26/26, 26/26 and 25/26 over the expanded 26-movement catalog; see the one-set Movement Practice entry below for the expansion that raised these).
The single bookend refusal at the x2.0 growth level is arithmetic rather than false precision: it is a stretch grown so far past any comparable one-set peer's work that no tolerance short of abandoning the ±1 minute promise would admit it, so the sweep asserts the coverage that actually holds (25/26) rather than a clean full sweep.
The player already reset `currentSet` to 1 on any swap, so a substitute with *fewer* sets than the slot the user was part-way through cannot strand them past its end; that is now pinned by a test rather than incidental.

The swap also carries the Return / Re-entry Ramp ease (US-E06).
`ReturnOverride.reentryScale` is resolved from the session's own `wasReturn` stamp plus the policy's ramp state - never re-derived against a fresh clock - so a substitute is held below full volume exactly as much as the slot it replaces, instead of one tap handing a returning user the single hardest slot in a session whose whole point is to be uniformly gentle.
This was the second Step 6 lever found missing from the swap seam, so all of them now flow through one private `overloadTarget` helper (the seam's only call into `AdaptiveOverload`, shared by the budget check and the materialized prescription), and a test pins the general property that every lever visibly moves the substitute's target rather than testing each one in isolation.
Routing every lever through one helper turned out to fix the levers but not their **scoping**: the helper passed the Start Seed for every candidate, while the assembler applies it only to strength and primal (`Builder.mobilityItems` sizes a stretch with `progressionRate` and `reentryScale` alone) so that warm-up, Movement Practice and cooldown are identical for a beginner and an advanced user.
Since Swap is offered on every step, an advanced cold-start user swapping a warm-up stretch was handed it at x1.30 - `mobility_forward_fold` at 39s beside 30s neighbours - and the budget check was then measured against that inflated target too.
The helper now passes the neutral volume for a `.mobility` candidate, and the scoping (not just the presence) of each lever is pinned by a test.

A follow-up accessibility pass fixed the *spoken* half of that same target line (`Views/ActiveSession/ActiveSessionView.swift`, `Views/Ready/ReadyView.swift`).
`targetAccessibilityText` spelled its counts out with fixed plurals, so any single-set slot read "1 sets of 45 second holds" - and the warm-up and cooldown are always single-set, which made that ungrammatical string the first and last thing a VoiceOver user heard in *every* session, however short.
The set count, the rep noun and the hold noun now each agree with their own number - the count through a shared `setsPhrase` ("1 set" / "3 sets"), and the article moving with the noun on a single hold ("1 set of a 45 second hold") - and the agreement composes with the per-side suffix rather than being swallowed by it ("1 set of a 30 second hold per side").
Every multi-set string is unchanged, so the change is purely additive to what already shipped.
The same pass removed a duplication an earlier review had flagged: `ReadyView` carried its own copy of the visual formatter and handed *that* string to its accessibility label, so the Ready Screen spoke the "×" glyph where the player spoke the nouns.
It now calls `ActiveSessionView.targetText` / `targetAccessibilityText`, which makes the player's two formatters the single source for both the seen and the spoken prescription and removes the second copy that let them drift apart.
The bug was reproduced before it was fixed: the added `ActiveSessionViewModelTests` cases fail on the prior implementation with the exact wrong strings, and `PerSideSwapEvidenceTests` gates the property end-to-end - every slot of a generated session has to speak counts that agree with its own numbers, and the Ready Screen's row labels are read back off the hosted view's live accessibility tree (not re-derived from the formatter) and asserted to match the player's sentence with no "×" anywhere on the screen.


US-O03 (`ViewModels/ActiveSessionViewModel.swift`, `Views/ActiveSession/ActiveSessionView.swift`, `Models/ActiveSessionState.swift`) is the **session timer redesign**: the running clock comes off the screen, and a clock that actually helps goes on it.

The always-on elapsed time is gone from both mid-session surfaces.
A total ticking up in the corner turns a five-minute session into something to get through and pulls attention off the movement, which is the opposite of what a discipline-first product wants; the total now lands once, on the completion summary.
The player's top bar and the rest overlay's were near-duplicates of each other, so both now render one `SessionTopBar` carrying the close control and nothing else - there is no second place for a clock to reappear.
The clock is **hidden, not removed**: `startedAt` and `elapsed(asOf:)` are untouched, so `completedDurationMinutes()` and everything reading it (the `WorkoutLog`, Default Duration learning, the Consistency Score, the summary's duration tile) behave exactly as before.
That the removal actually holds is asserted off the *live accessibility tree* of the hosted production player and rest overlay rather than assumed from the source, so re-adding the clock fails the suite rather than passing review.

In its place, a timed (`isHold`) exercise gets a per-exercise **Hold Timer**: the user taps "Start hold", a countdown runs in the demo's slot, and at zero the same accessible `RestTimerFeedback` cue the rest timer uses fires exactly once, the set records itself, and the player hands off to the rest.
Rep-based exercises are untouched - set tracker plus a manual "Complete set" - so the change is additive to two thirds of the catalog and load-bearing for the other third.

The hold is counted **one side at a time**, and that is the part worth spelling out.
The engine charges a per-side movement for both sides (`Exercise.isPerSide` via `sidesPerSet`, the same field US-O02's timing model prices a set with), so a set of `core_side_plank` is two 20-second legs, not one.
A single countdown that recorded the set at the end of one leg would quietly halve the work the session was planned around - which is precisely the failure the per-side target copy ("3 × 0:30 per side") was added to prevent, except worse, because a timer is an instruction the user follows rather than a label they read.
So a per-side hold cues the *switch* at the end of the first leg and parks on side 2 rather than auto-starting it: the tap that begins the second leg is the user's own time to change position.
Only the last leg records the set.
Four of the library's seventeen holds are per-side (`core_side_plank`, `mobility_9090_hip`, `mobility_pigeon`, `mobility_kneeling_hip_flexor`), so this is the ordinary case rather than an edge one, and both the button ("Start hold (side 2 of 2)") and the set tracker ("Side 2 of 2") name it.

Mechanically the leg runs against an absolute deadline, `pauseHold`/`resumeHold` are wired to the same `scenePhase` transitions the rest timer uses, and `completeHoldIfElapsed` is a pure idempotent check the view's ticker may call every tick - so the cue can never fire early, per-tick, or while the app is away.
It was first written as a full mirror of the rest timer, restore-from-snapshot included; that half of the mirroring turned out to be the root error of this story and was removed, so a leg no longer survives the player being torn down at all ("A hold is not a rest" below is where that lands and why).
What *is* persisted, in `ActiveSessionState.Hold` alongside `.Rest`, is the side - optional and defaulted so a snapshot written before this story decodes unchanged and an in-progress session is never lost to an app update.
The **side is persisted independently of whether a leg is running**: without that, a user who finished side 1 and backgrounded the app would come back on side 1 and do three legs of a two-leg set, which is the same halving bug pointing the other way.

One thing the story's own promise could not survive was left implicit in it, so it is fixed here too: a hold pauses on backgrounding, and iOS auto-lock backgrounds the app, so a user who sets the phone down to plank would have the countdown freeze and the cue that ends it never land.
The player holds `isIdleTimerDisabled` for as long as a session is being played - correct for an active workout screen generally, and load-bearing for this feature specifically - and hands the screen back to auto-lock on **completion as well as dismissal**, since the player is not dismissed when the session ends and the celebration screen has no countdown to protect.

The timer is the offer, not the only way through a timed movement.
A hold's primary action is "Start hold", but the row underneath keeps a quiet manual completion beside Swap and Skip, titled by the same `completeButtonTitle` logic every other slot uses ("Complete set" / "Finish exercise" / "Finish session").
Without it a timed exercise had no way to bank work at all: "Stop hold" records nothing by design, and Skip *discards* every set already recorded for the exercise - so a user interrupted on set 3 of a 3-set plank, or who held it off-timer, would lose the work rather than log it.
Most cooldown slots are holds, which made this the last control of nearly every session.
It stays offered **while a leg is actually running** too.
Hiding it there - on the tidy rule that the countdown is the only thing that records a set while it runs - left the running state with exactly two visible exits, and both destroy work: "Stop hold" records nothing, and Skip discards every set already banked for the exercise.
A user 25 seconds into set 3 of a plank who decides to stop would reach for Skip and lose sets 1 and 2 without being told.
The two-tap escape ("Stop hold", then the manual completion that reappears) existed but was not discoverable from the state the user is in, and an escape nobody can see is not one.
So the control is visible and enabled throughout: tapping it takes the running leg down through the existing cancel path - no cue, because coming out early is the user's choice rather than the timer's verdict - and then banks the set through the ordinary `completeSet`, which records exactly one set, resets the side, and opens the rest exactly as the countdown reaching zero does.
Trading a rule for a data-loss path is the right way round.
It also simplifies the row: every slot a timed movement carries is now always occupied, so `secondaryAction` no longer needs a hide-in-place mode at all.

Which *slots* that row carries is decided by the exercise rather than by whether a hold happens to be running, so starting one dims controls in place instead of removing them and the row never reflows under a thumb mid-tap.
The same principle settles the slot above it: the countdown is drawn inside the demo's own card (one `exerciseSlotCard()` shared by both), so starting a hold changes what is in the slot and nothing else - not the card under it, not the exercise name and target below it.
A timed movement also keeps "Start hold" as its primary action while a swap is in flight, merely unstartable, rather than briefly morphing into a different button.

That last point is the visible half of a real defect the review caught.
`canStartHold` did not consider `isSwapping`, so a hold started in the window between requesting a swap and the engine answering would keep counting down against the *substitute*, and at zero record a set of a movement the user never performed.
Both halves are closed: `canStartHold` refuses a leg while a swap is awaiting, and the `.substituted` branch now calls `resetHold()` rather than clearing the side alone.
The deliberate asymmetry either side of it stands - the pre-`await` call stays `endHold(fireFeedback:)` and `.noAlternative` still leaves the side untouched, because a swap that substitutes nothing must not charge the user a side they already held.

The same class of phantom set turned out to be reachable through a second door: **closing the player mid-hold**.
The snapshot kept the leg as running against an absolute deadline that was, by the time the user tapped Resume, already in the past - so the restored player's first tick fired the cue and banked a set within half a second of reopening, untouched.
Both ends of that are independently wrong and both are fixed.
Dismissal no longer leaves a countdown running on disk - first by freezing the leg on the way out, and finally by never writing one at all (the section below is where that lands).
What survives from that round either way is the ordering: `close()` reports the dismissal to the Ready Screen only once the last queued write has landed, so the resume card reflects the position the user actually left rather than the one before it.
That report hops to the main actor explicitly (`Task { @MainActor in … }`) rather than inheriting whatever a nonisolated method gives it, because `onFinish` reaches `ReadyViewModel.handlePlayerDismiss`, which mutates `@Observable` state SwiftUI is tracking; only `body` is implicitly main-actor, so the annotation is what makes that true.
The round that fixed the write end also made restore defensive about what it read, on the reasoning that a snapshot can predate this, be killed by the OS with no scene-phase transition, or simply be resumed days later: a leg still marked running whose deadline had gone by was brought back idle rather than finished.
That guard is gone now, because there is nothing left for it to guard - `init(state:)` reads the side and discards every other key a snapshot might carry, so no restore path ever sees a countdown.
The principle it was reaching for survived and hardened into the rule: an unfinished leg is unfinished work, and the user re-starts it deliberately.

Two smaller consolidations came with it.
The countdown ring was duplicated between the rest overlay and the new Hold Timer, so both now render one `CountdownRing`, and the two timers a user meets in a session read as the same object.
And the hold's countdown stands in `ExerciseDemoView.height` exactly, so starting a hold swaps the demo for the ring without shifting the exercise name and target underneath it - a jump that was visible in the first rendered pass and is gone in the second.

Adding a third column to that secondary row also made its narrowest case worth measuring rather than assuming.
Each column is roughly a third of a 393pt row, and the manual completion carries the longest title in it ("Finish exercise"), so at accessibility Dynamic Type sizes a fixed 60pt height would have clipped away exactly the words that say what the tap does.
The label now wraps and the row grows - the same remedy the target line already documents - with 60pt as the touch-target floor rather than a ceiling, measured off the live accessibility tree at both default and accessibility type (60pt vs 144pt) instead of only rendered.

Verification ran three ways in the Simulator, all against the production `ActiveSessionView`.
Rendered PNGs of the player at a hold (idle, running, idle at accessibility Dynamic Type, per-side side 1 and side 2), of the rest overlay, and of the completion summary that finally reports the total are under `artifacts/reports/us-o03/`, and `PerSideSwapEvidenceTests` is what writes them.
That is worth stating precisely, because it was not true at first: the evidence directory fell back to a machine- and session-specific path under `/var/folders`, so the committed images had been copied there by hand and any later change to the player's layout or copy would have left a stale render still cited as evidence.

US-O04 (`Utilities/UnitConversion.swift`, `Utilities/PressRepeater.swift`, `ViewModels/OnboardingViewModel.swift`, `Views/Onboarding/OnboardingView.swift`) puts **imperial units** in front of a US user without letting a single one of them past the onboarding boundary.
The app is metric everywhere behind the UI - `UserProfile` holds `heightCm`/`weightKg`, and `HealthKitWorkoutSample` prices a session as `MET x weightKg x hours` - so imperial is an input concern only, converted once on the way in.
That one-way discipline is why the arithmetic lives in a value type rather than inline in the view: a pound that leaks into the kilogram field silently inflates every calorie the app writes to Health by 2.2x, and nothing downstream would flag it.
`UnitConversion` carries the exact international definitions (1 in == 2.54 cm, 1 lb == 0.45359237 kg) plus the display/spoken forms, and `feetAndInches(fromCentimeters:)` rounds *total* inches before re-splitting them, so a height that rounds up to a whole foot reads `6 ft 0 in` rather than the `5 ft 12 in` that splitting first and rounding second produces.
It is also the only place the feet/inches split lives: the step holds a height as one number and the label overloads take that number, so no caller carries its own `/ 12` to drift from.
The step's bounds - 47...87 in, 70...445 lb - are the imperial cover of the 120...220 cm / 35...200 kg sliders they replace, rounded outward at every end rather than to convenient round numbers: 47 in is 119.4 cm and 87 in is 221.0 cm; 70 lb is 31.8 kg and 445 lb is 201.8 kg.
A narrower range would have been silent: there is no profile-edit surface yet, so a weight clamped on the way in under-reports every HealthKit energy estimate for the life of the account, and the story was meant to change the units, not who the app fits.

The view model stores only the imperial answers; `heightCm`/`weightKg` are derived, so there is no second representation to fall out of sync, and `buildUser` is the single place the conversion happens.
The defaults (`5 ft 8 in`, `175 lb`) are near the US adult median and deliberately *not* the values the PRD's validation test types, so a mapping that ignored its input could not pass by coincidence - a test asserts that separation directly rather than trusting it.

The repeat itself moved out of the view into `PressRepeater`, because the first version of it had three defects that no assertion could reach.
A tap gesture stacked on a long press gave one press two sources of increments - the tap recognizes on touch-up whatever the long press already did - so a press-and-hold ended a step past what the read-out had shown while it was held.
The repeat loop had no termination but cancellation, so holding `+` at the top of the range kept writing the same clamped value back through the binding about eleven times a second; Observation notifies on every write regardless of equality, so that is a real invalidation loop for no visible change.
And the step committed on touch-*down*, so a finger that landed on `+` on its way to scrolling the step had already moved the value, with the opposite button as the only recovery - a stray step charged to the user's own body measurements, which nothing downstream lets them correct yet.
The step now lands on *release*, which is what every other control in the app does.
Getting there took three passes at hand-rolled gestures, and each one broke on the same thing: deciding in the view whether a lifted finger was still *on* the button.
A `TapGesture` for the release and a press tracker for the repeat enforced different radii (a tap's ~10pt is not configurable, against the tracker's 22pt), so a press that drifted between them was tracked, never repeated, and then silently dropped - a button that read as dead.
Judging the release off the drag's own translation instead fixed that and introduced worse: a radius drawn around where a finger *landed* is not a button's bounds, so "still on the button" became a circle of the view's own invention, agreeing with neither the 44pt square it was drawn over nor any other control in the app.
So the geometry left the view entirely.
The button is now a real `Button`, and the single step is the platform's own touch-up-inside: the bounds that decide it are the ones every other control in the app gets, touch slop and all.
A press therefore stays with the button it landed on - a finger that lands on `+` and lifts a little over the adjacent `-` is still inside `+`'s slop and steps `+`, never `-`, exactly as two adjacent buttons behave anywhere else in iOS - and only travel past that slop, or a press the enclosing `ScrollView` takes over, commits nothing at all.
Inheriting that rule instead of restating it is the whole point of the change; the earlier hand-rolled radii are gone rather than retuned.
Only the drawing stays hand-rolled, in a `ButtonStyle` that renders the 44pt square.

That leaves `PressRepeater` the one job the platform has no notion of, against a `step` closure that reports whether the value actually moved: a press that outlives the hold delay repeats, and the release ending it adds nothing on top of what the read-out already showed, while a refusal ends the hold.
It runs off the style's own press state - true while the finger is down on the button, false the moment it lifts, drags off, or the scroll view takes over - so the repeat cannot outlive a press the view never heard end, and the same signal tints the glyph.
Being an object with an injected clock rather than gesture code is what makes it testable, and `PressRepeaterTests` gates it: nothing commits while the finger is down, a tap is one step on release whichever order the button reports the release and the end of tracking in, a press that ends anywhere but on the button moves nothing, a hold ends where it stood when the finger lifted, and a hold at the bound stops on the refusal.
The hold flag the release reads is cleared by whichever way the hold actually finished rather than by the next press: a reported release consumes it, and a repeat that ends on a refusal clears it on its way out - which is the case no release ever reports, since a hold that walks the value into the bound disables its own button under the finger and the lift fires no action.
Neither path can leave a stale `true` behind to swallow a later step, and a test drives exactly that sequence so the guarantee is pinned rather than asserted in prose.
The repeat task is also cancelled on deallocation, so a button torn down mid-hold on a path that never delivers `.onDisappear` cannot leave an orphaned loop walking the binding to the bound with no finger on screen.
Release semantics also cost the control its feedback - the value moving *was* the acknowledgement while it committed on touch-down - so the glyph now tints to the accent while pressed, cleared on release, on cancel and on disappear, and unanimated under Reduce Motion.
The tint fades in over 100ms and out over 200ms: a tap is often under 100ms, and SwiftUI's default 0.35s meant the highlight barely registered on exactly the interaction it was added to acknowledge.

US-T03 (`convex/schema.ts`, `convex/events.ts`, `convex/http.ts`, `convex/README.md`, root `package.json`) turns the `convex/` placeholder - a lone `.gitkeep` until now - into a real, deployed Convex project, and gives the funnel events a sink to land in.
It is the whole analytics backend: **one table, one mutation, one HTTP route**, and no app code changes at all (`ios/` is untouched, so the iOS build and every Simulator-hosted suite are unaffected by construction).
The `events` table carries five fields - `name`, `installId`, `clientTs`, `serverTs`, `props` - with no index beyond Convex's defaults and no funnel, cohort, or aggregate structure anywhere; `logEvent` validates, stamps `serverTs = Date.now()`, inserts one row, and returns.
The sink is dumb on purpose: every kill-criterion metric (K1-K8) is derivable from raw rows by a query written later, so a funnel baked into the write path would be a threshold decision made before there is any data to make it against - and the PRD forbids editing the pre-registered schema to move a threshold.
`convex/http.ts` is the part the US-T01 spike made load-bearing rather than optional: with `convex-swift` ruled out (arm64-only xcframework), `POST /logEvent` -> `204` is the client's **only** entry point, and US-T04's `URLSession` transport reaches it with no Convex SDK.
A third review round made that true of the sink as well as the client: `logEvent` shipped as a public `mutation`, which Convex exposes on the deployment's own `.convex.cloud/api/mutation` endpoint, so the sink had a second entry point that skipped every check in the action - and `.convex.cloud` shares its slug with the `.convex.site` origin a shipped binary carries, so it was reachable by anyone who read that URL. A direct call did insert a row with an empty `installId` and a `clientTs` of `0`. The empty `installId` is exactly what the boundary checks keep out of the column K4 counts unique installs by; the `clientTs` of `0` is not, and the docs no longer say otherwise - it is a finite JSON number, so it lands through the route as well, presence and kind being the whole of that check by design and range belonging to a query written later. It is an `internalMutation` now, reached as `internal.events.logEvent`, and nothing else calls it; `convex/_generated/` needed no regeneration because it derives the public and internal surfaces from the module's own types, and `npm run typecheck` confirms the switch by refusing `api.events.logEvent`. The identical direct call was then re-sent live at `99a11d0` and answered `Could not find public function for 'events:logEvent'` with no row inserted - the transport status being `200` in both the before and after cases, since Convex reports a missing public function in the response payload rather than as an HTTP status, so what proves the fix is that payload alongside the absent row.
Validation is exactly two rejections, because "basic input validation only" is an acceptance criterion: an unknown event name (a `v.union` of the 13 literals, generated from `EVENT_NAMES` - the same strings as `AnalyticsEventName`'s raw values, so the wire contract has one spelling per side) and an oversized property bag (>32 keys or >4096 **UTF-8** bytes serialized, both roughly two orders of magnitude above the widest real bag, `session_completed`'s four small scalars at ~120 bytes). The byte count goes through `TextEncoder` rather than `String.length`, which counts UTF-16 code units and would have undercounted a non-ASCII bag by up to a factor of three against a limit documented in bytes - the validation run gates that with 2100 `é` characters, only 2111 UTF-16 units but 4211 real bytes.
No per-key or per-type check: property vocabularies are expected to move during the PMF test, and a write-path check would turn every such move into a deploy.
The numeric convention is pinned at the wire form rather than patched up at the action - `clientTs` crosses as a plain JSON number, which already *is* the float64 a `v.number()` field stores, so the `int64`-vs-`float64` trap the spike documents never reaches Swift, while `generation_ms` rides untouched inside `props`.
The action adds one thing to that validation list and only one, and review is what put it there: the body's fields must be present and of the right kind - `name` one of the 13, `installId` a non-empty string, `clientTs` an actual JSON number - before they are handed to the mutation.
That is the same "so a malformed client cannot poison the table" criterion applied where untrusted input enters rather than a third rule, because coercing a missing field lands `String(undefined)` - the literal string `"undefined"` - and `Number(undefined)` - `NaN`, which Convex's float64 carries happily - into precisely the two columns the funnel is counted on: `installId` is the cohort key K4 counts unique installs by, `clientTs` is what K1 is timed from, and every such row would collapse into one shared phantom install.
A row that looks valid while being junk is worse than no row, and neither a bare `v.string()` nor a bare `v.number()` catches it downstream.
It constrains presence and kind only - no length cap, no format or UUID-shape check - and a numeric *string* is refused rather than coerced, because `Number("1e3")` and `Number("0x1f")` would land a silently reinterpreted value in the column K1 is timed from; a well-formed client, which sends a bare JSON number, is unaffected either way.
The two statuses are also no longer one: a rejection the sink asked for answers `400` carrying the message, while a deployment, runtime, or database failure answers `500` saying only `internal error`, with the detail left in the deployment log rather than echoed to a caller.
`logEvent` raises its own rejections as `ConvexError` rather than `Error` so the action can tell those two apart by a marker on the throw instead of by sniffing message text.
A fourth round narrowed that test to the one thing it needs: the classifier also carried a fallback for an `Error` merely *named* `ConvexError`, which no code path can produce - the SDK reconstructs a cross-isolate throw either as a genuine `ConvexError`, when it carries `data`, or as a plain `Error` named `Error` - and which would have echoed a raw internal message, stack frame and all, into a `400` body if it ever had fired. Recognising the marker is the whole test now, so only an error's structured `data` is ever echoed and everything else still falls through to the generic `500`.
A fifth round then made that single remaining test robust, because deleting the fallback left it as the only thing separating a caller's `400` from the sink's `500`. It recognised a `ConvexError` by `instanceof`, which the SDK itself pointedly does not use for this: the class stamps `Symbol.for("ConvexError")` on every instance and `registration_impl` detects one with `Symbol.for("ConvexError") in thrown`, because class identity does not survive duplicated module copies - and the package does ship two, `dist/cjs/values/errors.js` and `dist/esm/values/errors.js`, with the syscall layer reconstructing from a relative import while `http.ts` imports the `convex/values` specifier. Under a duplicated resolution `instanceof` would fail and every property-bag rejection would quietly turn into a `500`, manufacturing the outage signal the split exists to protect. The action now tests for the symbol, which every `ConvexError` carries whichever copy built it, and still reads only the error's structured `data` - a strict superset of what `instanceof` matched, so no verified response changed.
The split is entirely for a human: US-T04's client is strictly fire-and-forget and swallows every error, so an outage answered as `400` would be invisible - events would simply stop arriving and nothing would say so, and `4xx`-versus-`5xx` is the only signal anyone watching the PMF test gets.
A second review round found the split classifying by the wrong axis, which mattered because a hostile client could exploit it to manufacture what looked like a sink outage on the one signal that exists.
`ctx.runMutation` serializes its arguments with the SDK's `convexToJson` inside the action's own isolate, and that serializer refuses a field name starting with `$`, carrying a non-ASCII or control character, or over 1024 characters - so such a `props` key never reached `logEvent`, threw a plain `Error` rather than a `ConvexError`, and was reported as our `500`.
The action now runs the same serializer on the assembled arguments first and answers `400` when it refuses.
That is a classification rather than a rejection: the input was already refused either way, and borrowing the SDK's own function instead of restating its rule means the check cannot drift from what Convex enforces, while inspecting field names only - the per-key and per-type checks of `props` the story forbids stay absent.

US-T05 (`Utilities/AppState.swift`) gives the funnel the anonymous identity it is cohorted by, and nothing else: a handful of values on the existing app-state object, no transport, no emission, no `convex/` change, no touch to `Services/Analytics/`.
`installId` is a random UUIDv4 minted on first launch and kept only in `UserDefaults`; `firstLaunchAt` is when this install was first opened, or `nil` when that is unrecoverable; `lastActiveAt` is rewritten by `init`, which is its only writer - `AppState` is constructed once per process, so it moves on a cold launch and not on a resume from the background, and since iOS resumes far more often than it cold-launches, it can lag real usage by days.
It stays a settable `var` so a foreground update could move it, but nothing wires one and no story owns doing so; read it as "last cold launch" until that changes.
`installWeek` is a computed property, not a stored one, and it calls `ConsistencyScore.startOfWeek(_:_:)` - the same helper the Consistency Score's week bucketing uses - rather than re-deriving a week boundary.
The wire encoding is left to US-T07, which is where `install_week` first goes into a property bag and where `AnalyticsValue` having no date case has to be answered one way or another.
Where the id is **not** stored is the substantive part of the story. It is not derived from the IDFA, `identifierForVendor`, the Sign in with Apple identifier, or an email, and it is not in the Keychain - a Keychain item survives a plain uninstall with no restore involved, so a "deleted" install would come back wearing its old identity, which is the failure mode the account-deletion PRD names. `UserDefaults` is the mechanism, not an accident of convenience, but it is worth stating exactly what it buys rather than repeating the absolute the PRD's criterion uses: `Library/Preferences` is included in iCloud and iTunes backups and in device-to-device transfer, so the id dies with the app **absent a backup restore**, it can outlive an uninstall-then-restore, and one id can be live on two devices after a migration. K4's "distinct installs" carries that caveat; the storage is still right, because the gap between it and the Keychain is the whole point.
The clock, the calendar, and the generator are injected as `now: () -> Date`, `calendar: Calendar`, and `newInstallId: () -> String` on `init`, matching how `ConsistencyScoreService` and `OnboardingViewModel` already take their seams; `RepTodayApp`'s `AppState()` is unchanged. They are non-escaping because `init` is the only thing that uses them - `AppState` reads the clock exactly once, at construction, and never again.

Three launch states have to be distinguishable, and the first shape of this story only had two.
The id and its origin were read back as a **pair**, with anything short of both re-minted, which is right for a half-write that lost the *origin*: an id with no origin would otherwise cohort an install against a week it did not install in, silently wrong in the one column the cohort is grouped by.
But it also swept up the case that matters most at launch. An app that is *already installed* when this build ships has no `installId` key either, so it fell into the mint branch and got `firstLaunchAt` stamped with the upgrade date and `isFirstLaunch == true` - every TestFlight tester, dev device and shipped user would have been recorded as a brand-new install in the week they upgraded, inflating the K4 denominator and mis-cohorting the funnel the story exists to measure.
The discriminator is `isOnboarded == true` with no stored `installId`: such a launch mints an id, is **not** a first launch, and - absent an origin already on disk, see the second narrowing below - gets no first-launch date at all. `firstLaunchAt` and `installWeek` are therefore `Date?`.
Modelling the unknown as a real-looking date was the tempting alternative and is the worse one - a date with a caveat attached eventually gets read without the caveat, and US-T07 would emit a confidently wrong `install_week`; a `nil` forces that story to make a deliberate choice.
That optional then collides with the pair rule head-on, because an upgraded install is exactly the shape the pair rule calls corrupt (an id with no origin), and it would have re-minted its id on every single launch.
So the unknown is persisted in its own right, as `AppState.firstLaunchUnknown`, written beside the id: a stored id plus either an origin **or** that marker is a relaunch and is preserved; a stored id with neither is still corrupt and still re-mints.
The rule was then narrowed a second time, because "re-mint both" was always broader than its own justification. That justification only ever covered the case where the *origin* is the missing half; it never justified throwing away an origin that survived, and an onboarded install that reached the mint branch with a valid `firstLaunchAt` on disk had that date deleted and locked to "unknown" by the marker - destroying real cohort data to prevent a miscohort the stored date would not have caused. What the code does now, and what the rule actually is: **re-mint a missing or empty identifier, keep a usable stored origin whenever there is one, and fall back to unknown only when no usable origin exists** - which is also exactly what the `firstLaunchUnknown` marker records, rather than "the pair was incomplete". `isFirstLaunch` follows the same line: it is true only when this launch stamped the origin itself, so a re-mint that inherits an origin already on disk reports a new identity rather than a new install. The corrupt case is unchanged, because it has no stored origin to keep.
Reachability is low today - both keys are written in the same `init` and nothing clears the id alone - but a later "reset telemetry identity" affordance would clear exactly the id, and under the broader rule it would have silently wiped every onboarded user's cohort.
Keeping the origin does leave a state the emission story has to answer for, and it is now written on that story rather than left to be rediscovered: a re-minted id beside a surviving origin reports `isFirstLaunch == false` with a perfectly valid `install_week` available, so `app_install` either keys off the mint and double-counts one physical install, or keys off the origin stamp as it does today and leaves an id active in K4's numerator but absent from its denominator.
Both are lossy, neither is decided here, and US-T07 records which distortion it accepted; US-T06 carries the matching constraint not to ship a reset control before that answer exists, since that control is what makes the state reachable at all - and honoured it: its opt-out gates emission only, with two tests asserting the stored `installId` survives an opt-out untouched.
The residual, stated rather than glossed: a user who installed an earlier build but never finished onboarding still reads as a new install, because `isOnboarded` is the discriminator. Widening it to chase that case was declined.
`isFirstLaunch` is a stored `let` rather than something a caller recomputes, because construction is the only moment the fact exists - once `init` returns, a first launch and a relaunch are indistinguishable from the persisted values, and US-T07's `app_install` needs exactly that signal at exactly that point.

Two smaller corrections landed in the same pass.

It is now snapshotted as `previousActiveAt` (`nil` when there was no prior launch). Nothing reads it today, and to be clear about what it is not: the day-7 and day-30 return windows are measured from `firstLaunchAt` per FR-8, not from this.

What the pin also does is split two values that used to agree, and US-T11 now carries that as a criterion.

**Refinement of the AC's literal wording (captain-approved Option B, fixing a review finding).** The AC read "emit `session_abandoned` at dismiss-with-`completed==false`," but a mid-session dismiss **keeps the session resumable** (US-K04 does not clear the store): it is a *pause*, not an abandonment. Both give-up paths route through one private `emitSessionAbandoned(for:)`. The net invariant across the full resume path is **exactly one terminal event per physical session** (completed xor abandoned) - never both, never neither-when-an-outcome-occurred.
Because the give-up happens when the view model is already gone, `abandon_point` and `completed_minutes` are read off the persisted `ActiveSessionState`: `abandon_point` from the block the snapshot's current step sits in, and `completed_minutes` from a new `exercisedMinutes` field the snapshot captures at each meaningful change (the last active moment) - **not** recomputed as wall-clock `startedAt`->now at give-up, which would fold the idle gap between a pause and a much-later discard into the exercised total. The Consistency Score stays on `Calendar.current` because a user's training week is their local week. **The two calendars are coupled - do not change one without the other.**

### A hold is not a rest, and modelling it as one cost three review rounds

The Hold Timer was written by mirroring the rest timer: same absolute deadline, same pause-on-background, same restore-from-snapshot, same on-appear resume.
That was wrong in one specific way, and the way it was wrong kept producing the same defect through different doors.

A rest genuinely continues while the app is away - the user *is* resting - so restoring one mid-countdown is correct, and it is long-standing US-K04 behaviour.
A hold does not: the user stopped holding when they left the screen.
Because the hold restored the same way, every path that brought a snapshot back brought back a countdown already at or past zero, and the player's ticker then did exactly what it is built to do - fire the cue and bank a `CompletedSet` - for work nobody performed.
Three guards were written against three spellings of that state: a deadline already in the past, a frozen remainder of zero, and a frozen remainder that `onAppear` obligingly un-froze eighteen seconds after the screen appeared.
Each was a real fix; none was *the* fix, because the shape of the persisted state was never the problem.

The rule now is that **a hold leg never survives the player being torn down**.
Nothing about the countdown is persisted - only the side the user still owes - so a resumed session always comes back idle offering "Start hold" and the leg restarts on a deliberate tap.
There is no door left to guard because there is nothing to restore.
`ActiveSessionState.Hold` is a single field, and both a pre-US-O03 snapshot and one written by the earlier shape decode to the side they recorded, the running leg such a snapshot carries being exactly the thing that must not come back.
In-session backgrounding still freezes and resumes the leg through `scenePhase`, which is the interruption the user is actually present for; only the teardown boundary drops it.

The second half of the same lesson is why the rest timer had a milder version of the same bug - an expired rest firing its cue on the first tick after a resume - that no fix to the hold had ever touched.
`holdRemaining`/`pauseHold`/`resumeHold`/`endHold` were line-for-line copies of their rest equivalents, so a fix landed on whichever copy it was written against and survived in the other.
Both timers now run on one `Countdown` value type: absolute deadline, `pause`/`resume`/`extend`, and a `hasElapsed` that is false while paused, which is what makes the completion check safe to call on every tick.
Roughly eighty mirrored lines went with it.
What the two genuinely do differently stays in the view model where it is visible - a hold has sides and banks a set at zero, a rest has extend/skip and only cues.
The view half of this duplication had already been collapsed into one `CountdownRing`; collapsing the state half is what made the rest fix a consequence of the hold fix rather than a second thing to remember.

US-T14 (`convex/http.ts`, `convex/rateLimit.ts`, `convex/schema.ts`, `convex/crons.ts`, `convex/http.test.ts`, `ios/RepToday/RepToday/Services/Analytics/LiveAnalyticsService.swift`, `RepTodayTests/LiveAnalyticsServiceTests.swift`, `RepToday/Info.plist`, `project.yml`) abuse-hardens the public `POST /logEvent` action so a stranger who discovers the endpoint URL cannot flood the `events` table (the K1/K2/K4 evidence base) with junk rows. It adds **no** emission call site and leaves the US-T03 `events` row shape untouched.

**Two guards, both run before `ctx.runMutation`, so a rejected request never inserts.** (1) A **client-embedded shared secret** on the `X-RepToday-Analytics-Secret` header, compared **constant-time** (length-checked, XOR-accumulated) against the deployment's `ANALYTICS_SHARED_SECRET` env var: a missing or wrong secret is the caller's fault -> **`401`**, never `5xx`, so it never mimics a sink outage on the `4xx`/`5xx` signal a human watches during the PMF test; a deployment with **no** secret configured is **our** misconfiguration and **fails closed** -> **`500`** with a loud log, because an unguarded sink taking writes is the exact failure the story prevents. (2) **Per-caller rate limiting** (`internal.rateLimit.checkAndBump`) keyed on the per-install id (primary) with the coarse source IP (`x-forwarded-for`'s first hop, or `cf-connecting-ip`) as a backstop - **never** the shared secret, since every build embeds the same one and keying on it would collapse the whole user base into one bucket. Over-ceiling -> **`429`**, no insert. Ceilings live beside the code (`MAX_EVENTS_PER_INSTALL_PER_WINDOW` = 60, `MAX_EVENTS_PER_IP_PER_WINDOW` = 600, `RATE_LIMIT_WINDOW_MS` = 60_000); the window is anchored to **server** time (`Date.now()` stamped by the action and passed in as `nowMs`), never the client-supplied `clientTs` a flooder controls.

**The client mirrors the endpoint's inert-when-empty pattern.** `LiveAnalyticsService` sources the secret from a per-configuration `REPTODAY_ANALYTICS_SECRET` build setting (`project.yml` -> `Info.plist` key `RepTodayAnalyticsSecret`): Debug carries the dev deployment's secret, Release carries nothing, so `configured(...)` refuses to build a live service without one (`secret(fromValue:)` rejects missing/empty/whitespace/non-string) and a Release build resolves to `NoOpAnalyticsService` exactly as a missing endpoint already does - inert, never a stream of doomed `401`s. The secret rides on every POST via `secretHeaderField`, matching `ANALYTICS_SECRET_HEADER` in `convex/http.ts`.

**The counter store is a dedicated ephemeral helper table, not a second evidence surface.** `schema.ts`'s `rateLimits` table (FR-6's first permitted shape, a task-brief decision made over Convex's rate-limiter component to keep the suite fully in-process on `convex-test` with no new dependency) carries only `bucketKey` (`"<scope>:<identity>:<windowStart>"`), `windowStart`, and `count`, with `by_bucketKey`/`by_windowStart` indexes - no identity, no history, read only by the throttle. Baking the window into the key makes each window its own row, so stale windows are cleanly deletable. **A review round moved reclamation off the request hot path:** `checkAndBump` originally reclaimed expired rows opportunistically per request, which made concurrent requests from different installs contend on the shared `by_windowStart` range under Convex's optimistic concurrency and fail closed under exactly the launch-scale load the guard exists to survive. Reclamation now runs in a scheduled cron (`convex/crons.ts`, ~once a minute, `internal.rateLimit.reclaimExpired`) in bounded batches (`RECLAIM_BATCH`, raised to **2000** to comfortably outpace one flooding IP's ceiling-bounded inflow at that cadence), so the hot path does only point operations on the caller's own bucket. The accepted residual - a sustained single-source flood can transiently outpace one tick and let the table grow for the duration of the attack, draining once it stops - is documented in `convex/README.md` as the same determined-attacker case the guard explicitly does not defend against.

**Honesty is an acceptance criterion, stated in code and README both:** the client-embedded secret is extractable from the shipped binary and the per-install id is client-rotatable, so **both raise the cost** of abuse rather than preventing it - they stop opportunistic flooding of a freshly-discovered URL, not a determined attacker. No user accounts, no per-user auth, no ATT prompt, and no identity in events were added.

### Movement Practice is one set per stretch, and long sessions fill on more movement types

The engine used to grow the mobility Movement Practice block toward its time share by adding sets to a stretch (`allowSetAdjust: true`), so a real session produced "Cat-Cow Flow 2x10" and "Pigeon Pose 4x0:45 per side".
Multiple sets are redundant for a stretch, so `SessionAssembly.mobilityBlock` now builds it `allowSetAdjust: false` like the warm-up and cooldown - every exercise is exactly one set at every length (single-focus 5-10 and every blend), and the block fills a longer session only by promoting more distinct movement *types* from its reserve.

That change alone left long sessions short, because the block could no longer pad time and strength/primal were capped: a 60-minute mobility-leaning blend landed at 43.7 minutes (16 minutes under), the honest ceiling of the old catalog once the redundant sets were removed.
Two captain decisions resolved the fill, recorded here because the reasoning is not derivable from the diff.
First (long-session-fill): grow the mobility catalog rather than restore the set lever.
Then, when honestly filling 60 minutes with one-set stretches turned out to need ~21 distinct stretches in a single Movement Practice block - flagged as the pre-registered "18+ stretches is a product problem" gate - the second decision (stretch-count-60min): let the strength and primal blocks carry the extra time on long sessions instead.

The landed shape is all three: keep one set per stretch; a modest catalog expansion (12 -> 26 mobility movements, 14 new, distinct, zero-equipment, balanced across body regions with a mix of hold and dynamic durations) for within-session and cross-day variety; the Movement Practice block capped at `maxMobilityTrainingExercises = 14` so a session is never a 20+ stretch flow and day-to-day rotation keeps headroom; and the strength/primal set rail `maxTrainingSets` raised 4 -> 5 (the smallest lift that lands 45 and 60 minutes, and under the ~6-set "aggressive load" line the captain drew) so a long mobility-leaning session spends its overflow on legitimate strength volume, not padded stretches.
Every session length 5-60 now lands within the ±1 minute tolerance with stretches at one set.

The one-set rule was extended to the in-session swap surface for coherence: `ExerciseSwap.blockIsSetAdjustable` now returns `false` for `.mobility` too, so a swapped stretch can never be restructured into two sets - closing the same "multi-set stretch" bug on the path a user tap reaches, not only the generator.
The engine change is minimal (`SessionAssembly.swift` plus the one swap predicate); the rest is the catalog, the two tuning constants, doc-comment sweeps, and tests.

### Fuller length-scaled warm-up, and a strength bias for active users

Two captain-decided engine tuning changes, driven by product feedback that the opening warm-up read as too thin and that an active user's session read as movement-heavy by exercise count.
Block ordering (staleness-led Strength vs Movement Practice) is unchanged; both changes are isolated tunables, and determinism is preserved (no wall-clock reads, `asOf` threading unchanged).

First (warm-up thoroughness): the always-first `.warmup` block used to start at a single active movement and depend on the global timing fit to promote its reserves, so in practice it usually emitted only **one** stretch.
It now seeds directly at a length-scaled count - `SessionAssembly.warmupExerciseCount(forRequestedMinutes:)` returns ≤10 min 2, 11-20 3, 21-40 4, 41-60 5 - all active items with `minItems` pinned to that count, so a fuller warm-up is a deterministic property of the session shape rather than an accident of the fit.
`maxWarmupExercises` was raised `3 -> 5` as the pool-budget ceiling: the worst case (a long mobility-stale blend) draws warm-up 5 + cooldown 4 + Movement Practice 14 = 23 of the 26 mobility movements, leaving day-to-day variety headroom, and because the warm-up draws first and the cooldown before any Movement Practice block the cooldown is never starved.
The timing fit still lands every length within `toleranceSeconds` (verified across 5/10/15/20/30/45/60).

Second (active-user strength bias): a single tunable constant `PillarPlan.activeUserStrengthBias = 1.5` scales strength's weighted staleness in a *blend* only when `profile.sitsLong == false`; the sedentary path is untouched (bias `1.0`), so it *adds* a strength bias for active users without removing any of the mobility relief a desk worker gets (which lives in the single-focus lean).
It is the mirror image of that lean: a sedentary user gets same-day mobility relief and an unbiased blend split, an active user - not accumulating the postural debt that relief addresses - is nudged toward strength.
Concretely, for an active no-history user an otherwise-even blend shifts from 50/50 to 60/40 strength/mobility, giving strength more exercises/sets and Movement Practice one fewer; both pillars stay well inside the `minBlendShare`/`minExtendedBlendShare` rails.
It is deliberately one isolated constant so the magnitude retunes without touching the sedentary path or the staleness math.

`SessionAssemblyTests` and `PillarBalanceTests` were extended (warm-up sizing, pool-reservation headroom, cooldown-not-starved; active > sedentary strength share, active > the pre-change even baseline, and the share tied exactly to the constant).
Two pre-existing blend tests that assumed an even split for a non-sedentary user were retargeted to assert the *sedentary* even split, and `testBlendIgnoresSitsLong` was replaced (`testActiveUserBlendIsMoreStrengthForwardThanSedentary`) since blends now intentionally differ by `sitsLong`.

### Strength leads the blend too, mobility is a minority accessory (US-002)

The second story of the "Strength-Primary Sessions" PRD, the blend counterpart to US-001, again scoped to the engine mix only (no catalog change).
`PillarBalance.blendWeights(...)` no longer sizes the strength-vs-mobility split by staleness.
A blend is now a fixed strength-dominant envelope: mobility is a small minority accessory (`baseMobilityAccessoryShare = 0.2` -> ~80% strength / 20% mobility for an active user), and the old `activeUserStrengthBias` is recast as `sitsLongMobilityAccessoryBoost = 0.05`, which only enlarges the *desk worker's* mobility accessory to ~25% (FR-5: `sitsLong` modulates the accessory's size, never the lead).
`minBlendShare` drops from `0.3` to `0.2` so mobility is a genuine minority; both profiles keep strength in the ~0.75-0.80 target band.
Staleness now steers only the movement-pattern focus *within* the strength family (Step 3), not the pillar lead.
The extended blend (US-E02) keeps mobility the minority accessory and carves the dedicated primal block out of the leading strength family (strength + primal ≈ `1 - mobility`); only the within-family strength-vs-primal split still responds to weighted staleness / `pillarWeighting`, bounded by `[extendedPrimalFamilyFloor, extendedPrimalFamilyCap]` (0.2-0.45) so a stale or policy-favored primal earns a bigger block but never overtakes strength.
The now-dead `activeUserStrengthBias` and `minExtendedBlendShare` constants were deleted; warm-up/cooldown stay mobility and the timing fit is unchanged (a strength-dominant split is easier to fill via the strength/primal set lever, verified within ±60s at 15/20/30/45/60 for both `sitsLong` values).
`PillarBalanceTests` blend/extended sections were rewritten from the old co-primary/staler-leads/even-split expectations to the strength-dominant invariants (plus the US-002 validation).
`SessionAssemblyTests` retargeted the two shared-path assertions that encoded the old split: `testBlendSizesTrainingBlocksByPillarStaleness` became `testBlendGivesStrengthTheDominantShareRegardlessOfStaleness`, and the mobility-weighting test became `testHeavyMobilityWeightingCannotUnseatTheStrengthLead`; it also gained the per-pillar-seconds validation test and an all-lengths timing guard.
`PerSideSwapEvidenceTests` assumed the old mobility-led 30-min session (whose large Movement Practice block supplied the per-side holds); its `history()` was reordered so `core_side_plank` (a per-side strength hold) sits outside the `varietyWindow` and is selected as the core slot, giving the strength-led session its per-side hold.
Determinism and `asOf`-purity are preserved.

### Lean, length-scaled warm-up (US-003)

The third story of the "Strength-Primary Sessions" PRD: a leaner warm-up so it does not crowd out strength in a tiny session, while longer sessions still get a fuller opening.
`SessionAssembly.warmupExerciseCount(forRequestedMinutes:)` now returns **1 / 2 / 3 / 4** for the `≤10 / 11-20 / 21-40 / 41-60` bands (was `2 / 3 / 4 / 5`); the seeding mechanism (all active items, `minItems` pinned, one set each) is unchanged, so every session still deterministically opens with a warm-up block and there are no zero-warm-up sessions at any length.
`maxWarmupExercises` was lowered `5 -> 4` to stay the true ceiling the length-scaled count tops out at; the worst-case pool draw is now warm-up 4 + cooldown 4 + Movement Practice 14 = 22 of the 26 mobility movements, so the day-to-day variety headroom the reservation guard protects only grows, and the cooldown-not-starved invariant (warm-up drawn first, cooldown before any Movement Practice) is untouched.
The freed time from a leaner warm-up is reabsorbed by the fit loop through the strength/primal set lever and mobility-accessory types; every length lands within `toleranceSeconds` (verified across 5/10/15/20/30/45/60, and the PRD validation counts 1/2/3/4 warm-up movements at 5/15/30/60 with each session within ±60s of the request).
`SessionAssemblyTests` warm-up-sizing, pool-reservation-headroom, and cooldown-not-starved assertions were retargeted to the new counts (most derive expectations from `warmupExerciseCount`/`maxWarmupExercises` directly, so they track the change); only the count band and the ceiling constant moved.
Pillar balance, cold-start, and the Return override are out of scope and untouched; determinism and `asOf`-purity are preserved.

### Cold-start first week leads strength (US-004)

The fourth story of the "Strength-Primary Sessions" PRD: the cold-start counterpart to US-001/US-002, reversing the retired First-Week Contrast spread so the *first week* leads strength like the steady state does, kept gentle by the rails already in place.
`ColdStartOverride.overridePlan(...)` no longer rotates the day's lead pillar across `[.strength, .mobility, .primal]`: a single-focus plan becomes `.single(.strength)` outright, and a blend becomes `.blend(weights.favoring(.strength))`, so strength owns the largest block on every cold-start day while `favoring(_:)` preserves the share multiset (the blend still sums to 1 and no pillar is starved).
The now-dead rotation machinery was deleted - the `rotation` array, `contrastPillar(user:available:)`, and `startingPillar(for:)` - and `overridePlan`'s unused `template` argument was dropped (updating its one `SessionAssembly` call site); the `SessionAssembly` `.single(.primal)` branch stays as defensive degradation but is documented as unreachable now that no engine path produces a `.single(.primal)` plan.
The `forceContrastSpread` contract flag was deliberately **kept** as the Step 0 gate rather than ripped out (to avoid rippling into `SessionPolicy`/onboarding); its documented meaning is now "lead strength on cold-start days" (doc comments on `ColdStartContract.forceContrastSpread` and `ColdStartOverride.overridePlan` updated to match).
The gentleness rails are intentionally untouched and still apply exactly as before: the difficulty cap (`cappedMaxDifficulty` via `cappedPool`) and the Start Seed's reduced volume (`startSeed`/`startBandedPool`/`volumeSeed`).
Consequence by design: `why.openingBias`/`sitsLong` no longer steer the cold-start lead pillar (they still influence the underlying plan's accessory shares, which `favoring(.strength)` preserves).
`FirstWeekContrastTests` was rewritten in full to the strength-led invariant (renamed row "Cold-start strength lead" in `docs/test-coverage.md`), and the cold-start rotation/spread/primal-degradation cases in `SessionAssemblyTests` were rewritten to assert every cold-start single-focus day leads strength while proving the difficulty cap is preserved.
Determinism and `asOf`-purity are preserved (the cold-start "day" comes from `sessionsLogged`, never the wall clock).

### Returning-user comeback leads strength, kept gentle (US-005)

The fifth story of the "Strength-Primary Sessions" PRD: the Return counterpart to US-004's cold-start reversal, applying the same change to the other Step 0 gentle window so a comeback after a gap is a *gentle strength* session rather than the all-mobility session that prompted the whole PRD.
`ReturnOverride.overridePlan(_:isReturn:)` now leads strength: a single-focus Return returns `.single(.strength)` (was `.single(.mobility)`), and a blend Return re-points via `.blend(weights.favoring(.strength))` (was `favoring(.mobility)`), reusing the same `PillarWeights.favoring(_:)` share-swap US-004 used so the blend still sums to 1 and no pillar is starved.
The gentleness rails are intentionally untouched and still carry the whole comeback ease: the difficulty cap (`returnMaxDifficulty` via `returnPool`) and the reduced-volume floor / ramp (`reentryFloorScale` via `reentryScale`/`rampScale`). Return *detection* (`isReturn`/`daysSinceLastSession`, `returnThresholdDays`) and the cold-start/Return mutual exclusion are unchanged.
Doc comments describing the retired "led by mobility - the gentlest, same-day-relief pillar" behaviour (`ReturnOverride.swift` enum-level and `overridePlan`, plus the `SessionAssembly` call-site comment) were rewritten to the strength-led reality (strength leads; gentleness comes from the cap and floor).
`ReturnOverrideTests` pillar-plan assertions were retargeted to the strength-led invariant (`testReturnLeadsSingleFocusWithStrength`/`testReturnLeadsBlendWithStrength`) while the difficulty-cap and volume-floor/ramp tests still assert the gentleness rails hold; the end-to-end `SessionAssemblyTests` case was rewritten to `testReturnLeadsWithStrength` (the retired mobility-vs-staleness contrast is no longer expressible now that single-focus already leads strength in the steady state - the override and the steady state agree, exactly as cold start does), and the cold-start-suppression comment/message were de-referenced from the old "Return's mobility lead" wording.
Consequence by design (already accepted by the PRD for cold start and steady state): the returning desk worker no longer gets a dedicated same-day mobility-relief comeback; the comeback is strength-led, gentle via the rails.
Determinism and `asOf`-purity are preserved (the gap is a calendar-day difference against the injected `asOf`, never a wall-clock read).

### Update domain vocabulary and record the decision (US-006)

The sixth story of the "Strength-Primary Sessions" PRD: the vocabulary-and-record closer.
It changes **no engine behavior** - US-001..US-005 already made strength the leading pillar of every session (single-focus, blend, cold-start, and Return) with mobility demoted to warm-up + a minority accessory; US-006's whole job is to make the code's stated philosophy and the project docs reflect that strength-primary reality, and to durably record the co-primary -> strength-primary decision so a future contributor cannot re-introduce the old framing from a stale comment or doc.
The only `.swift` change is documentation: the `Pillar` enum doc note in `Models/Enums.swift` was rewritten from "`strength` and `mobility` are co-primary (Movement Practice is not a warm-up)" to state that strength is the primary pillar of every session and mobility is supporting (warm-up, cooldown, and a minority accessory block), keeping the accurate part that Movement Practice is a real training block, not the warm-up; the stale "co-primary" explanatory comment on `ExerciseLibraryTests.testPillarCoverage` was likewise corrected (no assertion changed).
Two knowledge artifacts were created: a root `CONTEXT.md` capturing the resolved domain glossary (Pillar, Movement Practice, discipline-first), and `docs/adr/0001-strength-primary-sessions.md`, the first ADR in a new `docs/adr/` directory, recording the co-primary -> strength-primary shift, its motivation (the reported all-mobility 5-minute session), and its sharpest captain-accepted trade-off (a 5-10-min-only user gets mobility solely as warm-up, and desk workers lose a dedicated same-day mobility-relief day; `sitsLong` now only modulates mobility-accessory volume, never the lead).
`docs/test-coverage.md` and `AGENTS.md` were verified to describe the strength-primary session mix with no surviving current-tense co-primary/mobility-lean assertion (AGENTS.md sections 2 and 7 already read strength-primary; the implementation-log's US-001..US-005 "old co-primary" references are past-tense historical records and were left as written).
The GTM package (`gtm/**`) still carries co-primary marketing framing and was deliberately not touched: GTM positioning is captain-owned and tracked under a separate task.
No test logic changed; this is a documentation-only branch, so the unit suite stays green unchanged.

### Cross-cutting strength-primary regression guard (US-007)

The seventh and final story of the "Strength-Primary Sessions" PRD: a consolidated regression guard.
It adds **no engine, enum, or catalog behavior** - US-001..US-005 already made strength the leading pillar of every session and US-006 recorded the decision; US-007's whole job is one consolidated test (`ios/RepToday/RepTodayTests/StrengthPrimaryRegressionTests.swift`) that pins the strength-primary invariants across the whole length x mode matrix so a future tuning change cannot silently reintroduce a mobility-only session (the original bug: a 5-minute desk-worker session generated as all stretches).
The suite sweeps requested lengths `5/10/15/20/30/45/60` across three generation regimes - steady-state, cold-start (US-004's First-Week window), and Return (US-005's post-gap comeback) - through the real `SessionAssembly.assemble` pipeline (reusing existing fixtures, no new engine plumbing), and asserts: (1) every session has a real `.strength` training block and is never mobility-led (the leading training block by planned time, computed with the engine's own `workSecondsPerSet`, is strength), with single-focus 5-10 min carrying no `.mobility` training block at all; (2) the strength-share bands - single-focus ~100% strength (>= 0.8 floor); a blend's strength **family** (strength + any dedicated primal block US-E02 carves at 41-60 min) inside the US-002/US-003-validated `0.7...0.88` band with a genuine mobility accessory present and strength leading primal, plus a dedicated check that the representative 20/30 blends sit near the ~0.75-0.80 target; and (3) determinism and `asOf`-purity (byte-identical repeat at a fixed `asOf`; re-anchoring now+history a year later yields the identical session), reaffirming rather than loosening `DeterministicSessionPolicyServiceTests`/`SessionAssemblyTests`.
The band is measured on the strength **family** rather than strength-alone because at 45/60 min the engine correctly splits off a dedicated primal block (strength alone ~0.56, family ~0.8) - matching how `PillarBalanceTests` pins strength+primal == 0.8.
A `docs/test-coverage.md` row was added per convention, and the xcodegen-regenerated `project.pbxproj` registers the new test file; the full unit suite stays green (969 tests, 1 skipped opt-in benchmark).

### Remove the Movement Practice block; reallocate its minutes to strength (US-M01)

The first story of the "Movement Practice removal + pattern-matched bookends" follow-on (a later, separately-dated design pass on top of US-001..US-007).
US-001/US-002 made strength the *lead* of every session but kept mobility alive as a small **Movement Practice** accessory *training* block on 11-60 min sessions - the last place a "blend" still meant a strength-vs-mobility split rather than a pure strength session with mobility bookends. US-M01 removes that block outright and reallocates its minutes to strength (captain decision 3 - pure relocation into the bookends was explicitly rejected), so the reported movement-heaviness is fixed in fact, not just relabelled.
The **split machinery is removed, not neutralized** (decision 4): `Services/Engine/PillarBalance.swift` is **deleted** (the whole `PillarStaleness`/`PillarPlan`/`PillarWeights` file), and `SessionAssembly.buildBlocks` no longer takes a `PillarPlan` - it builds the block skeleton directly from the `SessionShapeTemplate`: a warm-up, then a single **strength** training block (primal folded in) for single-focus and the shorter blends, or a strength block plus a dedicated **primal** block for an extended (41-60 min) blend, then a cooldown past `cooldownThresholdMinutes`. There is no mobility middle block at any length; mobility survives only as the warm-up and cooldown bookends (whose selection logic US-M01 leaves untouched - that is US-M02/M03).
The **strength lead is now structural** rather than an emergent property of the deleted staleness math: because the training middle is always a strength block, the lead is unconditionally strength, so `ColdStartOverride.overridePlan` and `ReturnOverride.overridePlan` (which existed only to force the lead to strength) are removed - cold-start and Return now contribute only their gentleness rails (the capped pool and the eased volume). This is the collapse-the-lead-to-a-constant the follow-on called for; the US-001/002/007 "strength present and leading in every session" invariants stay green.
**Primal is untouched** (decision 1): folded into the strength block on short sessions, its own block at 41-60 min. Its size is now a fixed minority of the training budget (`SessionAssembly.extendedPrimalTrainingShare = 0.15`) in place of the deleted staleness-weighted within-family split - strength keeps a clear majority (>0.80 of training) so the freed mobility minutes accrue to strength. Two engine constants were recalibrated: `maxTrainingSets` `5 -> 8`, because the strength/primal set lever is now the *only* training lever and must carry the whole of a long (45/60 min) session that the many-stretch Movement Practice block used to help fill; timing still lands every length within ±60s.
The now-inert policy/contract fields (`SessionPolicy.pillarWeighting`, `ColdStartContract.forceContrastSpread`) are kept and documented as inert (still decoded/seeded so persisted policies round-trip), rather than removed, to avoid churning the Codable/Programmer surface for a later story.
**Expected test churn** landed as the follow-on flagged: `PillarBalanceTests` (whole suite) was deleted; the `overridePlan`/`PillarWeights` unit tests in `ReturnOverrideTests`/`FirstWeekContrastTests`/`ColdStartHandoffTests` were removed; `SessionAssemblyTests` and `StrengthPrimaryRegressionTests` were rewritten to encode the strength-wrapped-in-bookends shape (no mobility middle block at any length, freed minutes -> strength, strength share above the archived ~0.75-0.80 model). One evidence test (`PerSideSwapEvidenceTests.testRenderPlayerAtAPerSideRepMovement`) drove a per-side rep off the removed mobility block, so it now seeds a per-side rep **strength** frontier (Bird Dog) to render the same UI case. Docs updated: the six US-M01 acceptance boxes flipped in the PRD, `CONTEXT.md` (Pillar entry + "Movement Practice (retired)"), `docs/adr/0001-strength-primary-sessions.md` (a US-M01 update note; the strength-lead invariant stays, the accessory-block clause retired), `docs/test-coverage.md`, and the `Pillar`/`SessionAssembly` doc comments.
US-M03..US-M05 (`sitsLong`-as-bias, uniform-vocabulary copy, and the extended regression guard) remain spec-only, separately-authorized later tasks.

### Pattern-matched, prefer-then-fill bookends (US-M02)

The second story of the follow-on. US-M01 left the bookends' *selection* logic untouched; US-M02 makes the warm-up and cooldown **earn their stretches** by leading with one that complements the day's lead strength pattern (captain decision 5).
Each of the 26 mobility movements in `Resources/Exercises.json` gains a `complements: [MovementPattern]` tag encoding the captain-approved mapping (squat/hinge/push/pull/core, every pattern resolving to >= 6 stretches). On the model, `Exercise.complements` is optional (`[MovementPattern]?`, `nil` default) so strength/primal movements omit the key and an already-persisted `Exercise` decodes unchanged; `MockExerciseService.validate` now fails a mobility movement that is *missing* the tag (`ExerciseLibraryError.mobilityMissingComplements`) - an empty `[]` is valid, an absent key is a tagging omission - so the schema stays honest.
The engine change is a **prefer-then-fill bias, never a filter**: `SessionAssembly` resolves the day's lead strength pattern once (`leadStrengthPattern()` = the stalest strength pattern, strength-only so the target is always a mapped pattern even when primal is folded in) and threads it into both bookends; `orderedMobility` runs its existing deterministic staleness / no-repeat sort and then `leadingComplement` promotes the single best-variety complementing stretch to the front, leaving the rest untouched. When nothing complements the lead (or the lead is `nil`), the ordering stands unchanged, so the general pool is the fallback and a bookend is never starved or emptied. The reorder reads no clock and depends on no set-iteration order, so assembly stays deterministic and `asOf`-pure; bookend counts and the US-M01 ±60s timing fit are unchanged (only *which* stretch leads changes).
New coverage in `BookendComplementSelectionTests` (see `docs/test-coverage.md`); the six US-M02 acceptance boxes are flipped in the PRD, and `CONTEXT.md`/`AGENTS.md` gained a one-line pointer to the new field and the prefer-then-fill behavior. US-M03..US-M05 remain spec-only.

## Owed work

Carried here rather than on a story, because nothing in the funnel or MVP PRDs owns it; it is recorded so the exception cannot quietly become a second sanctioned way of doing things.

**`OnboardingBasicsEvidenceTests` should adopt the shared evidence-suite seams.**
`AGENTS.md` states two rules in the absolute - a suite never rolls its own evidence path (`EvidenceOutput.directory(for:)` is the one resolver, and `REPTODAY_EVIDENCE_DIR` names a **root** with the story folder appended), and hosting a production surface goes through `HostedSurface.host(_:size:)` / `AccessibilityTree` so every suite gets the same run-loop settling.
Both rules stand as written, and every suite written since honours them. `OnboardingBasicsEvidenceTests` is the single exception, and it predates them: it landed with its own preamble and was never migrated, so the absolutes describe the bar rather than the current state of that one file.
Adoption covers five things, listed because a partial migration would leave the file looking converted while still diverging: its private `UIHostingController`, its `UIWindow`, its private `pump(...)`, its private accessibility walk / `accessibilityElement(labeledWithPrefix:in:)`, and its `evidenceRoot` - which resolves `REPTODAY_EVIDENCE_DIR` as the **final** directory, with no `us-o04` folder appended, so one redirected run scatters its render into a different layout from every other suite's baselines.
A sixth is a value rather than a seam and is the one with a visible output: the suite captures at `format.scale = 2` while `HostedSurface.captureScale` is 3, so the committed `artifacts/reports/us-o04/` baseline is at a different scale from every other committed render and adopting `HostedSurface.capture(_:size:)` will regenerate it larger. That is expected, not a regression, and the refresh is part of the work.
Deliberately not done inside US-T06: it is a code change to a suite that story has no business refactoring, and the alternative - softening the two `AGENTS.md` sentences to match reality - would have lowered a bar the repo set on purpose while leaving a future reader unable to tell a weakened rule from an intended one.
Pointers back to this entry sit at `HostedSurface.swift`'s doc comment, at the head of `OnboardingBasicsEvidenceTests`, and in `AGENTS.md` beside the two rules.
