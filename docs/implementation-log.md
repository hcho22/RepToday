US-E05 (`Services/Engine/AdaptiveOverload.swift`) tunes Step 6's per-cycle bump curve into the **Asymmetric Ramp** - back off fast, climb slow: a single recent `too_hard` or a **skip** of the exercise pulls the next target down eagerly (`hardStep` steepened to `0.80`, a 20% back-off), while `too_easy` climbs only patiently (`easyStep` gentled to `1.10`, a 10% rise) and `justRight`/unrated nudges up by the gentlest `progressiveStep` (`1.05`), so the down-step magnitude is always >= the up-step (`(1 - hardStep) >= (easyStep - 1)`, asserted on the constants) and every signal still moves by at least one so direction is never lost to rounding. The `too_hard`/`too_easy` mapping plus the new skip signal are resolved into a private `RampSignal` (`eased`/`intensify`/`progress`): `demonstratedCapacity` now scans past a skipped most-recent entry to read the set count and per-set value from the earlier worked session but remembers the skip and forces `.eased`, so a recent bail eases the target (below capacity) even over an earlier `too_easy`, without the skip becoming the capacity *source*. The ramp composes with US-E03's `progressionRate` unchanged - the rate still paces only the two advancing steps, never the eager down-step - and stays within the existing rep/hold/set rails.
US-E06 (`Services/Engine/ReturnOverride.swift`, `Services/Engine/SessionAssembly.swift`, `Services/Engine/AdaptiveOverload.swift`, `Services/Engine/PillarBalance.swift`, `Models/Workout.swift`) completes the Epic E engine extensions with the **Return override** and the **Re-entry Ramp** - discipline overriding optimization after a gap. `ReturnOverride.isReturn` flags the next session a Return once the calendar-day gap since the most recent logged session reaches `returnThresholdDays` (7, pure over `asOf`, `false` for a fresh no-history user), and while a Return is active - and cold-start is not; the two are mutually exclusive, the Return gated off by `ColdStartOverride.isActive` since cold-start already serves gentle capped sessions - `SessionAssembly` serves an easy, winnable session *regardless of staleness or the policy's optimization levers*: `overridePlan` leads with mobility (a single-focus Return trains it directly, a blend re-points its shares to favor mobility via the now-shared `PillarWeights.favoring`, extracted from `ColdStartOverride`), `returnPool` caps the eligible pool at `returnMaxDifficulty` (2, never emptying it), and `reentryScale` eases Step 6's volume to the gentle `reentryFloorScale` (0.70). The Return itself carries no readjustment; the readjustment lives in the Re-entry Ramp: `sessionPolicy.reentry.rampSessionsRemaining` (seeded to `rampSessions` = 3 by the Programmer after a Return, US-F03) drives `ReturnOverride.rampScale`, which walks the volume scale from that floor back to neutral `1.0` as the counter decrements, so `AdaptiveOverload.target` (now taking a `reentryScale:` - neutral `1.0` by default, applied only to capacity-derived per-set targets, and always landing at least one below the un-held target down to the rep/hold rails) holds difficulty below normal on the sessions after a Return and climbs it back. The Return decision is made once (the shared `SessionAssembly.isReturnSession`, gating both the overrides and the flag) and stamped on the assembled `Workout.wasReturn`, so the post-session log-writer (US-L01) records it onto `WorkoutLog.wasReturn` (US-D02) rather than re-deriving detection at a different `asOf`. Every override is a pure function of its inputs and a no-op in the steady state, so a present, warmed-up user runs exactly the US-E03 pipeline; with US-E06 done the Epic E engine extensions are complete, and Epic F (the AI Programmer that writes the policy, including seeding the `reentry` ramp on a `return` trigger) is next.
The v6 Epic F AI Programmer has begun: US-F01 (`Services/Programmer/ReprogramTriggerDetection.swift`) opens the on-device, deterministic Programmer with **re-program trigger detection and Trigger Precedence** - the detection half of the seam whose re-weighting lands in US-F02/US-F03. `ReprogramTriggerDetection.dueTriggers(user:recentLogs:library:asOf:calendar:)` is a pure function returning the due `ReprogramTrigger`s (US-D04) in precedence order, so the client can re-program on open against the highest-precedence one without any server clock and the new policy applies one open later. It detects the four PRD kinds: `weekly_boundary` (the injected calendar's `weekOfYear` for `asOf` is strictly later than the most recent log's week, so a just-closed Consistency-Score week exists to re-tune against - never for a no-history user), `return` (reuses `ReturnOverride.isReturn`, the single Return-detection seam so the Programmer and engine can never disagree on what a Return is), `physical_stall` (for each chain the user has worked, the frontier tier - the highest-order worked tier, the same notion Step 5 uses - has an existing next tier (`progressionId != nil`) yet its parsed `AdvancementCriteria` are cleared in `stallClearedSessions` = 2+ distinct sessions while the frontier never rises, meaning that real next tier is gated and the user is genuinely stuck; a single-tier or top-of-chain movement has nothing to advance to and never stalls, so the library's easily-met single-tier mobility chains never misread a healthy user as a plateau), and `disengagement` (over the most recent `disengagementWindow` = 3 completed sessions, the per-session completion ratio `durationMinutes / requestedMinutes` - clamped to 1 - forms a declining non-increasing run whose newest value falls to <= `disengagementCompletionRatio` = 0.6, or a window skip rate >= `disengagementSkipRate` = 0.5; reading the requested-vs-completed gap rather than absolute completed minutes is deliberate per US-D02, so a user who intentionally requests shorter sessions and finishes them - Default Duration learning - is never misread as pulling away, and lengthening gaps are already the Return trigger). **Trigger Precedence** is enforced at the source - when both apply, `disengagement` suppresses `physical_stall` so a user pulling away is never handed more challenge - and the returned order (`return` < `disengagement` < `physical_stall` < `weekly_boundary`) mirrors it. Detection is pure and deterministic over `(user, recentLogs, library, asOf)` - the clock is injected as `asOf` and stamped onto each trigger's `detectedAt`, never read from the wall clock - and needs the validated `library` only to resolve advancement criteria and chain position for the stall signal; the concrete `SessionPolicyServiceProtocol` (US-F03) supplies the library and adapts this to the protocol's library-free `dueTriggers(user:recentLogs:asOf:)` (the shell `MockSessionPolicyService` still reports no triggers until then).
US-F02 (`Services/Programmer/PlateauDiagnosis.swift`) adds the Programmer's **plateau diagnosis** - telling a *physical stall* (capacity earned but gated) apart from *disengagement* (pulling away) and mapping each to the Session Policy levers US-F03 writes.
The two plateau predicates that US-F01 detected inline (`isPhysicallyStalled(recentLogs:library:)` and `isDisengaging(recentLogs:)`, with their tuning constants `stallClearedSessions`/`disengagementWindow`/`disengagementCompletionRatio`/`disengagementSkipRate`) now live here as the single seam, and `ReprogramTriggerDetection.dueTriggers` composes them rather than re-deriving them - so detection and diagnosis can never disagree about what a stall or a disengagement is (the same pattern by which US-F01 reuses `ReturnOverride.isReturn`), a behavior-preserving move that leaves US-F01's trigger output unchanged.
`PlateauDiagnosis.diagnose(recentLogs:library:) -> Plateau?` returns the single plateau in force (`.physicalStall`/`.disengagement`) or `nil`, applying the same Trigger Precedence at the source (disengagement wins, so a diagnosis can never hand more challenge to a user pulling away); it is pure over `(recentLogs, library)`, reading only log history (the completion ratio and skip rate are the consistency signals, straight off the logs per US-D02) with no clock, and needs the `library` only to resolve advancement criteria and chain position for the stall.
The **explicit lever mapping** `PlateauDiagnosis.reweighted(_:for:)` moves only the affected levers on a passed-in policy and leaves `version`/`updatedBy`/`note`/persistence to US-F03: a `.physicalStall` multiplies `progressionRate` by `stallProgressionBoost` (1.15) and widens `varietyWindow` by `stallVarietyWiden` (+1) for a capable-but-gated user, while a `.disengagement` eases `progressionRate` by `disengagementProgressionEase` (0.85) and narrows `varietyWindow` by `disengagementVarietyNarrow` (-1) - lower difficulty, less novelty - and never raises challenge; both are clamped to the rails (`minProgressionRate`/`maxProgressionRate` 0.5...2.0, `minVarietyWindow`/`maxVarietyWindow` 1...6) so recurring plateaus accelerate or ease without running away.
The session-length half of "less friction" for disengagement is delivered by Default Duration learning (US-F04) - the policy carries no session-length lever, so the mapping does not fabricate one.
US-F04 (`Services/Programmer/DefaultDurationLearning.swift`, `Services/Programmer/PolicyNote.swift`) adds the Programmer's two honesty pieces - both pure, deterministic, and left to be wired by the re-weighting service (US-F03), the same way US-F01/US-F02 provide pure logic no service yet calls.
`DefaultDurationLearning.learned(_:completing:)` (and its `from recentLogs:` convenience) folds newly-completed session `durationMinutes` - what the user *finishes*, never what they *request* (US-D02) - into `User.Duration.completedDurationEWMA` (a `smoothingFactor` 0.3 EWMA whose prior is the existing average, else `onboardingSeedMinutes`, so learning is anchored to the stated preference until real evidence accrues), then sets `defaultMinutes = snappedToChip(ewma)` against the ascending `chipValues` (5/10/15/20/30/45/60), a boundary snapping to the shorter/gentler chip; `onboardingSeedMinutes` is never mutated and empty input is a no-op, so a user requesting 20 but completing ~12 drifts the default to 10/15 while the caller (US-F03) avoids double-counting by folding each session once.
`PolicyNote.templated(policyBefore:policyAfter:durationChange:)` builds the user-visible `SessionPolicy.Note` (always `source == .template`) from the **real diff** - the direction `progressionRate`/`varietyWindow` actually moved plus any Default Duration change - never from the trigger's intent: it names a stepped-up challenge / eased intensity and fresher / familiar movement only when the levers moved that way, appends the new go-to duration only when it changed, returns `nil` when nothing observable changed (the honest outcome), and never invokes the user's `why` (no hollow motivation callback), so the note can only ever claim a change the sessions actually reflect.
US-F03 (`Services/Programmer/DeterministicSessionPolicyService.swift`, `Persistence/CoreDataSessionPolicyStore.swift`, `DI/ServiceContainer.swift`) completes Epic F with the real, persistence-backed re-weighting service that finally composes the Programmer's four pure pieces (US-F01 detection, US-F02 diagnosis + lever mapping, US-F04 Default Duration learning + templated note) into the `SessionPolicyServiceProtocol` the client will call on open.
`currentPolicy(for:)` reads the last-written policy from an injected `SessionPolicyStore` (or `SessionPolicy.default` until one exists), and `dueTriggers(user:recentLogs:asOf:)` adapts US-F01's library-taking detection to the protocol by supplying the validated catalog from the exercise service.
`reprogram(user:recentLogs:trigger:)` writes a fresh policy: it moves the optimization levers for the trigger (`physical_stall`/`disengagement` re-diagnose the freshest history through `PlateauDiagnosis.diagnose` and apply `reweighted`, so **Trigger Precedence holds end-to-end** - a stall trigger can never accelerate a now-disengaging user; `return` seeds `reentry.rampSessionsRemaining` to `ReturnOverride.rampSessions` = 3 and touches no optimization lever, discipline overriding optimization; `weekly_boundary` moves no lever on its own), folds Default Duration learning over only the non-Return sessions completed after the current policy's `updatedAt` (the `updatedAt` cutoff is a dedup boundary so the EWMA folds each session exactly once across re-programs - `default`'s 2001 sentinel epoch folds the full first history - and `wasReturn` sessions are excluded because their deliberately short, capped duration (US-E06) would drag the learned default down and soft-penalize a celebrated comeback), stamps `version += 1` / `updatedBy == .deterministic` / `updatedAt = trigger.detectedAt` (time injected, never the wall clock), attaches `PolicyNote.templated(...)` built from the real before/after diff (so the note can only claim a change the sessions reflect, and is `nil` when nothing observable moved), and persists the learned `user.duration` first (via `UserServiceProtocol`, only when it moved, since policy and user are separate aggregates) then the policy (via the store), so the policy's `updatedAt` dedup boundary only advances after the duration derived from those sessions is durably saved. The service **never generates or returns a workout**; it only writes policy. Persistence is a `SessionPolicyStore` protocol with an `InMemorySessionPolicyStore` (tests/previews/the mock container) and a `CoreDataSessionPolicyStore` (the running app, backed by `CDSessionPolicy` so the policy survives relaunch and offline use, US-J02 will sync it); the real service is wired into `ServiceContainer.mock()` in place of `MockSessionPolicyService` (the one-line swap), returning the default until it has written a policy so pre-programming behavior and `ServiceContainerTests` are unchanged. With US-F03 done the Epic F AI Programmer is complete; the on-open *client invocation* of `dueTriggers`/`reprogram` lands with the Ready Screen (US-J02).

`SessionPolicy.ColdStartContract` now carries a **Start Seed** alongside the US-G01 cap: `startingDifficultyFloor` (**beginner 1 / intermediate 2 / advanced 3**) plus the volume seed `startingRepMultiplier` / `startingSets` (**x1.0 & 3 sets / x1.15 & 3 sets / x1.30 & 4 sets**), all filled by `ColdStartContract.seeded(for:)` from `profile.fitnessLevel` (so onboarding's US-I01 `seedInitialPolicy` seeds them with no change of its own). The engine reads the seed in the same Step 0 gate as the cap (cold-start active *and* a contract present), so it retires with cold-start (US-G04) and a warmed-up user runs exactly the US-E03 pipeline.
`ColdStartOverride.startBandedPool` bands the **strength and primal** pool to `[startingDifficultyFloor, cappedMaxDifficulty]` under the already-applied cap, so Step 5's lowest-eligible selection for a no-history user starts at the *band entry* rather than the chain's entry tier (an advanced user's first push is a difficulty-3 pike/diamond push-up, not a wall push-up). Mobility is never floored - the warm-up, Movement Practice, and cooldown all draw from it and a stretch's difficulty is not training load - so warm-up/mobility/cooldown are byte-for-byte identical at every level; and the band can never empty a movement pattern: the floor is clamped down per pattern to the hardest movement that pattern actually offers inside the cap.
The floor is tuned against the library a Discipline-Phase user can actually *reach*, not the nominal 1-5 scale: setting each level's floor equal to its own cap collapsed the "band" to a single tier and landed intermediate and advanced on the same movements, so the floor sits a tier beneath the cap instead, which keeps each band a real range and the two pools genuinely different (intermediate opens the whole 2-3 band, advanced only its top).
Sitting the floor beneath the cap was only half of it, because the reachable catalog itself was too short. `ExercisePoolFilter` gates `phase == .strength` out for every MVP user, and the shipped library put every gated skill at difficulty 5 with nothing Discipline-reachable above 3 - so the advanced `[3, 4]` band resolved to seven movements, and five of the six banded patterns offered exactly **one** progression chain inside it. Chains, not movements, are what the variety window rotates over: Step 5 resolves a pattern by picking one exercise per chain, so a single in-band chain hands the user the identical movement every session of the week however many tiers that chain carries. The answer was to extend the *reachable* range rather than weaken the band or unlock the Strength Phase early - earning that phase is a product principle, not a gate to route around. `Resources/Exercises.json` grew from 42 to 57 movements with fifteen zero-equipment Discipline tiers at difficulty 3-4 (archer push-up; cossack and shrimp squats; marching glute bridge and long-lever single-leg bridge; bear hold, hollow rock and tuck L-sit; a whole `pull_horizontal` chain of wall scapular pulls and supine floor rows; a `primal_ground_flow` chain of gorilla walk and lizard crawl; and, closing the last single-tier gap, an underswitch and a bear-hover shoulder tap so `locomotion` finally carries difficulty 4 too), slotted into existing chains where one continued and into new chains for the two patterns that had only one. Phase now gates *skills* rather than tiers - the three gated movements are the library's difficulty-5 summit, and every tier beneath a summit is reachable - and two standing gates hold the band open: `ExerciseLibraryTests.testAdvancedStartBandHasRoomToRotate` keeps at least two in-band *chains* per banded pattern, and `testEveryBandedPatternSpansTwoTiersInsideItsStartBand` at least two in-band *tiers*, so a `[floor, cap]` label can never sit on what is really a single difficulty.
The Zero-Equipment Floor is about the *room*, not just the kit, so four of those first thirteen were re-authored: a doorway row, two table rows and a Nordic curl negative all satisfied `equipment == []` on a technicality while quietly requiring a door frame, a table that would hold body weight inverted, or anchored ankles. They are replaced at the same difficulties by movements that need only a floor and a wall - a wall scapular pull, a supine floor row and its single-arm progression, and a long-lever single-leg bridge - so `apartmentFriendly: true` is a fact the library states rather than a flag a test had to certify.
Banding also left a cliff on the far side of the handoff, and that one is an engine flaw rather than a content gap.
A chain the band withholds is never prescribed, so it accrues no history; the session `ColdStartHandoff` clears the contract, its untouched entry tier is the only candidate the variety window has never seen, and freshness alone would hand an advanced user a difficulty-1 wall sit.
Three rounds of trying to fix it with a difficulty *floor* in Step 5 established that the approach was structurally wrong rather than merely mis-implemented: a floor is a lower bound, while the Return override, the `too_hard` de-escalation, and the skip escape hatch are all upper bounds, so putting them on the same dial produced a fresh collision every round - the floor inverted the Return cap, then permanently retired whole progression chains once a pattern reached difficulty 4, then anchored itself to an onboarding self-report nothing ever revises, then switched itself off on a routine skip.
The fix is to remove the conflict instead of refereeing it.
Freshness has exactly one blind spot - it cannot tell "the user outgrew this" from "the engine never let them see this" - so `ColdStartOverride.withheldByStartSeed` names the movements the band held out of reach and Step 5 stops counting those as new: `selectInChain` enters a no-history chain past them, and `select(pattern:)` sets them aside before consulting the variety window.
Nothing is filtered and nothing is forced, which is what makes the ceilings win for free rather than by precedence rule.
A Return caps the pool at difficulty 2, which leaves nothing in-band to prefer, so every candidate comes back into scope and the gentlest tier is served exactly as it was before the band existed - and the same is true of an injury filter or any other narrowing.
A `too_hard` session eases the seed itself, and the withheld set is resolved from that same eased seed, so the tier the seed just reopened stops being withheld in the same move.
A skip changes nothing here at all.
The withheld set is a factual claim about the user's own cold-start week rather than a policy dial, so it is recorded rather than re-derived.
While cold start is active it is the live seed; on the session that retires the band `ColdStartHandoff` writes the floor the week actually ran at - the seed as eased by every `too_hard` rating it produced - to a new additive `User.ColdStart.bandFloorAtHandoff`, and afterwards Step 5 reads exactly that.
Only that rating moves the tier: a skip is the product's escape hatch ("not this movement") and eases the seeded *volume* alone, mirroring the Asymmetric Ramp, so a routine tap cannot permanently erode a band that outlives the log window.
The contract's un-eased aim is recorded beside the floor as `bandAimAtHandoff`, because the retiring session's own rating is collected on the completion screen and therefore always lands after the handoff has run; `ColdStartHandoff.revisedBandFloor` re-resolves the recorded floor from that aim when it does, touching no counter, so an explicit `too_hard` on the fifth session still reaches the band the rest of the account is measured against.
Deriving it at selection time instead was the first attempt and it does not survive: the engine's `recentLogs` is a bounded 70-day window (`ReadyViewModel.recentLogLookbackDays`), so the cold-start sessions - and the `too_hard` rating that eased the floor - age out, after which a derivation quietly re-raises the tier the rating lowered and starts asserting a band the user never lived through.
The field decodes to `nil` when absent, which reads as "no banded cold start ever ran" and withholds nothing: correct for a record persisted before US-O02 (whose contract decodes its Start Seed to the neutral floor, so that week genuinely ran unbanded), for a contract carrying the neutral floor, and for any generation against `SessionPolicy.default`.
That closes the second half of the problem too - `coldStart.active == false` is equally true *before* a contract exists as after one retires, so gating on the flag alone had been asserting a band retroactively over users who never had one.
`StartSeedTests.testSessionAfterTheHandoffNeverRegressesBelowTheColdStartTiers` is the standing gate - it walks a full five-session cold start and asserts the sixth session regresses in no pattern, including one that week never trained.
`ColdStartOverride.volumeSeed` hands the volume half to Step 6: `AdaptiveOverload.target` gains `startingRepMultiplier`/`startingSets` parameters that scale **only the no-history default target** - the very first prescription of a movement, where there is no demonstrated capacity to be relative to - clamped to the existing `maxReps`/`maxHoldSeconds`/`maxSets` rails; a capacity-derived target (session 2+ of that movement) ignores the seed entirely, and the neutral values reproduce the pre-seed target precisely. `SessionAssembly` applies it only to the strength and primal blocks, matching the floor's scope.
The safety net for an over-reported level corrects the **tier**, not just the volume. The Asymmetric Ramp (US-E05) still eases reps eagerly on a `too_hard` rating or a skip, but on its own that would hold a user at an unwinnable tier for the whole five-session cold-start window, since the band removes every gentler tier from the pool. `ColdStartOverride.startSeed` therefore resolves the *whole* seed against `recentLogs`: it counts the same eager down-signals the ramp reacts to (a session rated `too_hard`, or one where the user bailed on a strength/primal movement) and steps the floor down a tier, drops a set, and eases the rep multiplier by the ramp's own `hardStep` per signal - never past neutral, and never touching a beginner's already-neutral seed. Tier and volume ease together on purpose: de-escalating onto an easier movement the user has never logged would otherwise re-apply the full volume seed to it.
The in-session swap (US-C08) now carries the seed across its seam: `WorkoutEngineProtocol.swapExercise` takes the `sessionPolicy`, which `ReadyViewModel` -> `ActiveSessionView` -> `ActiveSessionViewModel` thread through from the policy the session was generated against, so `ExerciseSwap` sizes a substitute with the same Step 6 levers (`progressionRate`, the Start Seed, `varietyWindow`) as the rest of the lineup instead of silently re-deriving it at the neutral seed. The default `SessionPolicy.default` argument reproduces the pre-policy swap exactly.
Finally, the seeded target is reflected in the **planned wall-clock**.
`Exercise.estimatedTimePerSetSeconds` is one constant calibrated against the movement's own default per-set value, so reading it directly assumed every set was prescribed at that default.
It is also not pure per-unit work: getting into position, bracing, switching sides and getting out again is paid once per set whether the set is 8 reps or 20, and in the catalog that fixed part is often the bulk of the estimate (`mobility_9090_hip` carries a 70s estimate on a 30s hold).
`SessionAssembly.workSecondsPerSet` therefore splits the estimate into a fixed per-set **setup** cost plus a **per-unit** cost.
Exactly one of the two halves has to be assumed and the other read off the movement's own authoring, and which way round matters.
A hold's per-unit cost is known a priori - one second of work per prescribed second, *per side* for an `isPerSide` movement, because a "20 second" side plank is 20 seconds left plus 20 seconds right - so its setup is the authored remainder `estimate - sides × defaultDurationSeconds`, which the catalog puts at 5-25s.
A rep has no authored duration to anchor that half, so for reps the *setup* is the assumed one (`setupSecondsPerSet`, capped by `maxSetupShareOfEstimate`) and the cadence is the authored remainder `(estimate - setup) / defaultReps`.
That is the right way round because cadence genuinely varies per movement - the catalog spans `hinge_glute_bridge` at 15 reps in 40s to `push_one_arm` at 3 in 50s - while getting down onto the floor and back up is much the same work whatever the movement is.
The first attempt had it backwards: it pinned the per-rep cadence at a global 3.0s and let the setup absorb the entire residual, which misclassified everything that genuinely scales with the target as a fixed cost and so *under*-charged per-side and slow-tempo movements, in places worse than the strict-proportional model it replaced (a `core_side_plank` grown to 40s was priced at 65s against 85s of real holding - a 60s under-count from a single slot over three sets, the whole ±1 minute budget).
That constant was also circular: it was calibrated from the four rep entries it then assigned zero setup to, asserting they have no setup at all.
`setupSecondsPerSet` is calibrated from a different family instead - the holds, where the setup is *observed* rather than fitted, and whose authored remainders have a median of exactly 10s.
Both halves reproduce the authored estimate exactly at the movement's own default, so a default-sized session is priced precisely as the catalog wrote it and only a moved target is re-priced - which keeps the ±1 minute timing promise honest for a x1.30 first session and for any capacity-grown one, without the strict-proportional model's systematic over-charging or the per-side-blind split's under-charging (a 40s `mobility_9090_hip` hold costs 90s; a 40s `core_side_plank` costs 85s; `push_archer` at 8 reps costs 74s rather than 59s; a hold clamped to `maxHoldSeconds` costs its setup plus the hold on every side, not a scaled estimate).
The per-side signal is a new additive `Exercise.isPerSide` rather than a parse of the user-facing `advancementCriteria` copy, so timing does not silently depend on wording; it is optional (absent means not per side) so an older `Exercises.json` and an already-persisted active session still decode, and a library test cross-checks the flag against that copy in both directions.
That cross-check originally matched a closed whitelist of per-side phrases, which meant an unfamiliar wording ("3x8 clean reps per arm", natural for the upper-body chains) simply fell through to "not per side" and the movement was silently under-timed by half - the exact failure the gate exists to catch.
It now asserts *positively* that every criteria string matches one of a small set of recognised authoring templates, with a second backstop that no criteria may name a limb at all outside a recognised per-side marker, so an unanticipated phrasing fails loudly instead of defaulting.
Making the per-side cost explicit also exposed two rails that were per-side-blind.
`AdaptiveOverload.maxHoldSeconds` is documented as a safety rail against an absurd prescription, but for a per-side hold it meant three minutes *per side* - a single set costing more than the entire budget of a 5-minute session - so `clampPerSet` now divides the ceiling by `sidesPerSet` and the rail means what its doc says for every movement.
That matters because the timing fit's only levers are set counts and item promotion/dropping: it can never shrink a per-set target, and warm-up, Movement Practice and cooldown all carry `minItems: 1`, so an unbounded per-side hold could push a short session past ±60s with nothing available to adjust.
The clamp does bound it - a fit case driving every per-side hold in the catalog to its rail now lands inside ±60s at all five durations, and fails without the clamp.
The existing ±1 minute tests could not have caught this: they run against history sitting near the movements' rep defaults with no holds at all, which is precisely the configuration where the split and the doubling are both no-ops.
Finally, the loop is closed in the player: `targetText` and `targetAccessibilityText` now read "3 × 0:30 per side" and "3 sets of 30 second holds per side", driven off `isPerSide` so the copy cannot drift from what the engine charges.
Previously the per-side instruction appeared only in `advancementCriteria`, which is progression copy rather than the prescription, so a user handed a 40s side plank who held it once did 85s less work per set than the session was planned around - over three sets the whole ±1 minute budget from one slot.
One point worth recording so it is not re-litigated: the work half of a session is never *timed*.
Nothing counts a rep or a hold down, the only countdown in the player is the rest timer, and a completed set logs the target it was prescribed rather than anything measured.
So this is a planning-only quantity whose single job is fitting a session to the minutes the user asked for; chasing per-second accuracy on a self-paced activity would be false precision.
What matters is that the model carries no *systematic* bias, because a consistent per-slot error accumulates where random error averages out - and that is exactly what both of the failed models had.
Because an advanced seed opens at `startingSets == maxTrainingSets`, the fit also lost its "add a set" lever entirely, so reserve promotion now enumerates every set count within the rails rather than only the count Step 6 prescribed; without it a 10-minute advanced session parked 91s short of the request.
The seeded **set count** remains a pre-fit starting volume - the timing fit may still trade sets against the duration the user asked for, and the requested duration wins.
The swap's slot-budget check is measured through that same model.
It resolves the candidate's `OverloadTarget` first and prices **both** sides with `SessionAssembly.workSecondsPerSet` at the target each actually carries, so `slotToleranceSeconds` bounds the session's real wall-clock rather than two movements' default-sized estimates - previously a capacity-grown 20-rep `push_diamond` slot accepted a never-logged `push_pike` opening at its 8-rep default on a reported drift of zero while the session lost minutes.
Honouring the real budget on its own, though, did not merely narrow the candidate pool - it very nearly removed the feature.
A substitute the user has never logged always opens at its own default while the slot it replaces carries a grown target, and at a fixed set count the 30s tolerance leaves only ~10s of per-set headroom: sweeping the Discipline strength/primal catalog found an in-budget peer for 42/42 movements at the default target but only 18/42 at x1.5 of it and 3/42 at x2.0 - and x1.5 is ordinary, since `push_standard` opens at 8 reps and advances at "3x12".
The fix is the **set count**, the same lever the assembler's own timing fit uses, rather than a wider tolerance.
`ExerciseSwap` now picks the substitute's set count inside `minTrainingSets...maxTrainingSets`, comparing full slot seconds (`sets × workPerSet + (sets - 1) × rest`) so the rest a set change adds or removes is counted - rest being the one part of the budget that is exactly known.
The original count wins whenever it is already in budget, so a swap restructures a slot only when leaving it alone would push the session out of its stated minutes, and `.noAlternative` is reported only when no permitted count fits.
Making that promise actually true took a second pass: `bestFitSets` settles each candidate's *own* best count, and the selection then compared drift across all of them, so drift outranked set-preservation and slots were restructured gratuitously - `push_standard` grown to 10 reps returned `push_wall` at **4 sets** (drift 18) when `push_diamond` fit at the original 3 (drift 27), and with no growth at all `mobility_pigeon` returned `cat_cow` at **2 sets** when `mobility_9090_hip` fit at 1.
Catalog-wide that was 40 such cases at 3 sets/40s rest and 28 at 1 set/15s rest.
Set-preservation is now the *first* selection criterion, so drift is compared only among candidates that fit the slot as built and a re-picked candidate is reachable only when none does; both named cases now return the same-set peer, and the gratuitous count is 0 in each configuration.
The lever is scoped as the assembler scopes it: the warm-up and cooldown are built `allowSetAdjust: false`, so a bookend slot keeps its single set and simply declines instead - which required `ActiveSessionViewModel.snapshotForSwap()` to stop collapsing the lineup into one strength block and preserve the real block structure, since the block is what makes that distinction visible to the seam.
Because a bookend has no lever *and* no rest, a flat 30s gate there is the strictest test applied to the softest quantity, so a non-adjustable slot gets `slotToleranceSeconds + 0.3 × its estimated work` instead.
The 0.3 is read off the catalog rather than picked: across all 57 movements the widest gap between a movement's own per-set work at its default and its nearest in-band peer's is 30% (`mobility_pigeon` at 100s against `mobility_9090_hip` at 70s; the 95th percentile is 14%), so the band is exactly wide enough to admit every pair the catalog itself authors as equivalent and no wider, and it is additive so a very small slot keeps the flat allowance rather than a tighter one.
Measured over the sweep in the **adjustable** 3-set/40s-rest shape, coverage recovers to 42/42, 38/42, 41/42 and 38/42 at x1.0/x1.25/x1.5/x2.0 of the Discipline strength/primal catalog, and the flat 30s tolerance is unchanged there.
That shape is the one where the set lever always exists, so it is now measured alongside the real bookend shape (1 set, `mobilityRestSeconds`, non-adjustable), where the 12 mobility movements cover 12/12, 12/12, 11/12 and 11/12 at the same four growth levels.
The single bookend refusal is `mobility_pigeon`, and it is arithmetic rather than false precision: grown to 68s per side it is 146s of work against a nearest in-band stretch of 70s, which no tolerance short of abandoning the ±1 minute promise would admit, so the sweep asserts the coverage that actually holds rather than 12/12.
The player already reset `currentSet` to 1 on any swap, so a substitute with *fewer* sets than the slot the user was part-way through cannot strand them past its end; that is now pinned by a test rather than incidental.

The swap also carries the Return / Re-entry Ramp ease (US-E06).
`ReturnOverride.reentryScale` is resolved from the session's own `wasReturn` stamp plus the policy's ramp state - never re-derived against a fresh clock - so a substitute is held below full volume exactly as much as the slot it replaces, instead of one tap handing a returning user the single hardest slot in a session whose whole point is to be uniformly gentle.
This was the second Step 6 lever found missing from the swap seam, so all of them now flow through one private `overloadTarget` helper (the seam's only call into `AdaptiveOverload`, shared by the budget check and the materialized prescription), and a test pins the general property that every lever visibly moves the substitute's target rather than testing each one in isolation.
Routing every lever through one helper turned out to fix the levers but not their **scoping**: the helper passed the Start Seed for every candidate, while the assembler applies it only to strength and primal (`Builder.mobilityItems` sizes a stretch with `progressionRate` and `reentryScale` alone) so that warm-up, Movement Practice and cooldown are identical for a beginner and an advanced user.
Since Swap is offered on every step, an advanced cold-start user swapping a warm-up stretch was handed it at x1.30 - `mobility_forward_fold` at 39s beside 30s neighbours - and the budget check was then measured against that inflated target too.
The helper now passes the neutral volume for a `.mobility` candidate, and the scoping (not just the presence) of each lever is pinned by a test.
