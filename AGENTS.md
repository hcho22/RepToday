## Project Overview

Rep Today is a discipline-first micro-workout iOS app (5-60 min sessions) for busy, desk-bound adults.
The user says how many minutes they have, and a deterministic on-device engine generates a complete zero-equipment session blending bodyweight strength and mobility - no browsing, no choosing, no thinking.
Strength is earned, not the entry promise: every user starts in the **Discipline Phase** and earns the **Strength Phase** through sustained consistency plus demonstrated competence, so all MVP users resolve to Discipline with the `PhaseEvaluator` already in place.
The MVP is Apple-native with no custom backend behind the core loop (the `convex/` telemetry sink is beside it, not under it); AI/LLM features are deferred to Phase 2, do language only, and never generate or adapt a workout.

- **Fourth, in-progress PRD - round cap and wide circuits:** `.claude/agent/tasks/prd-round-cap-wide-circuits.md` (`US-RC##`). Caps every training-block exercise at **2-4 rounds** (down from `1...8`) and fills a longer session by going **wider** - more distinct movements, drawn from a strength pattern's *further* progression chains as accessories - instead of deeper. **US-RC01 has landed** (engine-only, the coupled core): `SessionAssembly.minTrainingSets`/`maxTrainingSets` are now `2`/`4`; `Builder.strengthBlock` seeds the reserve breadth-first over `ProgressionChainSelection.selectAll` (every pattern's primary chain first, stalest pattern first, then every pattern's further chains as accessories), and the extended blend's dedicated `primalBlock` does the same over its one pattern's two chains (the PRD's stated fallback, exercised because a beginner's 60-min session lands short without it); every promoted station still joins at the block's uniform round count (ADR-0003 unchanged). Landing this exposed and fixed two latent timing-fit bugs the round cap made load-bearing: `candidates()`'s whole-station promotion now searches the round count *jointly* with adding the station (`.addReserveWithRounds`) rather than pricing it at whatever round count the round-only lever had already walked to (which could turn the one available widening move into an overshooting jump); and `ProgressionChainSelection.selectAll` ranks every chain by freshness/withheld-status as a sort key rather than an elimination filter, so a pattern's non-frontmost chain no longer vanishes from the reserve just because its sibling chain was recently worked. `RoundCapWideCircuitsTests` is the story's own coverage; `SessionAssemblyTests.testEvidenceEvenRoundCircuitTranscriptAcrossLevelsAndLengths`'s precision bound loosened from ±3s to ±10s under the coarser, station-quantized lever (worst observed deviation 8s, still far inside the real ±60s `toleranceSeconds` gate). **US-RC02 has also landed** (test-and-docs-only, no production/engine change): `RoundCapInvariantGuardTests` (routinely-run `RepTodayTests` bundle, deliberately distinct from US-RC01's `RoundCapWideCircuitsTests`) is the standing regression guard - it assembles sessions across 5/10/15/20/30/45/60 min and all three fitness levels and asserts every training-block station's `sets` (circuit blocks per `SessionAssembly.isCircuit`; linear bookends exempt) sits in the **literal** `2...4` and each training block is internally even (ADR-0003). The range is bound to hard-coded `2`/`4`, *not* `SessionAssembly.minTrainingSets`/`maxTrainingSets`, so bumping a constant cannot silently loosen the guard - non-vacuity verified 2026-08-18 (reverting `maxTrainingSets` to 8 makes it fail, restoring `2...4` makes it pass). **US-RC03 has also landed** (test-and-docs-only, no production/engine change; `AccessoryProgressionParityTests`): a wide-circuit **accessory** progresses and is dosed exactly like a primary because the parity is **structural**, not added machinery - Step 5's `ProgressionChainSelection.selectAll` ranks every chain through one `selectInChain` (an accessory is simply a lower-ranked result of that same call, bound by the identical advancement, Start-Seed-band, and `varietyWindow` rules) and Step 6's `SessionAssembly` `appendTrainingItem` doses every station (seeded primary, other patterns' primaries, and every accessory) through one `AdaptiveOverload.target` call, so there is no separate accessory code path. ## Build & Run

```bash
cd ios/RepToday && xcodegen generate    # regenerate the project from project.yml
xcodebuild -project ios/RepToday/RepToday.xcodeproj -scheme RepToday \
  -sdk iphonesimulator -configuration Debug \
  -destination 'generic/platform=iOS Simulator' build
xcodebuild -project ios/RepToday/RepToday.xcodeproj -scheme RepToday \
  -destination 'platform=iOS Simulator,name=iPhone 16' test
xcodebuild -project ios/RepToday/RepToday.xcodeproj -scheme RepTodayUITests \
  -destination 'platform=iOS Simulator,name=iPhone 16' test    # XCUITest suite, run on demand
```

The `RepToday` scheme builds the app and runs `RepTodayTests` - that is the default run, and everything except the XCUITests lives in it; if the destination will not resolve, use `xcrun simctl list devices available` and pass `-destination 'id=<UDID>'`.
One suite in `RepTodayTests` is deliberately held out of that default run: `SessionGenerationBenchmarkTests`, the re-runnable session-generation latency harness behind the `<100ms` claim (the session-generation benchmark record, 2026-08-10), is **opt-in and skipped** (so the gate and CI never pay its ~17.5k-generation cost) unless you pass `RUN_SESSION_BENCHMARK=1` to xcodebuild - a build setting the `RepToday` scheme forwards into the Simulator process exactly like `REPTODAY_WRITE_EVIDENCE` below; it is re-targetable to a real device unchanged via `-destination`, and the Simulator run is an optimistic proxy, not the authoritative iPhone XS / iOS 17 number.
Target iOS 17.0+, Swift 5.9, Xcode 16.3, bundle id `com.reptoday.app`.
`RepTodayUITests` is a second scheme on purpose: it installs and launches the app in a booted Simulator and drives it out of process, so folding it into `RepToday` would make every unit run wait on an app launch and inherit its failure modes.
Run it when the touch path is what is in question - it is the only place a production control is actually pressed rather than hosted.
`DEVELOPMENT_TEAM` is set to the signing team, so entitlement-gated paths (Sign in with Apple, CloudKit sync, HealthKit writes, live purchases) build for device; they still verify only on real hardware, never in the Simulator.
Historical device notes in `docs/implementation-log.md` and the PRDs predate this and describe the team as empty - read them as point-in-time records.
The evidence suites (`PerSideSwapEvidenceTests`, `OnboardingBasicsEvidenceTests`, `ProgressTabSnapshotTests`, `HandsFreeBookendEvidenceTests`, `USCC08PaceEvidenceTests` - the last also writing a `pace-report.txt` transcript beside its PNG) render production screens to PNGs on every run, and `OnboardingImperialUITests` screenshots the running app the same way, but a plain `test` writes them to a per-run temporary directory so the worktree stays clean; append `REPTODAY_WRITE_EVIDENCE=1` (a build setting, since a Simulator-hosted test bundle inherits no shell environment - both schemes forward it) to regenerate the committed images under `artifacts/reports/<story>/`, or `REPTODAY_EVIDENCE_DIR=<root>` to send them elsewhere.
A suite never rolls its own path: `EvidenceOutput.directory(for:)` is the one resolver, and `REPTODAY_EVIDENCE_DIR` names a **root** with the story folder appended - never the final directory - so one redirected run keeps the same `<root>/<story>/<file>` shape as the committed baselines instead of scattering suites' renders into different layouts.
The XCUITest screenshots are produced on demand rather than committed: the suite always files them with its `.xcresult` too, so the two variables only decide where a second, browsable copy lands.
`TelemetryOptOutUITests` also renders the screens US-T06 added, but files them **only** as `.xcresult` attachments and reads neither variable - it wants a picture a reviewer opens on a green run, not a baseline to diff. So the PNGs committed under `artifacts/reports/US-T06/` are **not** written by any run: no suite resolves that directory, their names and count do not match the suite's attachment names, and `artifacts/reports/US-T06/validation.md` cites them as evidence - so refresh them deliberately and keep the existing filenames rather than expecting `REPTODAY_WRITE_EVIDENCE=1` to regenerate them.
Hosting a production surface to capture or read it likewise goes through `HostedSurface.host(_:size:)` and `AccessibilityTree`, so every suite gets the same run-loop settling rather than an ad-hoc copy that reads a half-drawn screen.
Both of those rules have exactly one known exception, and it predates them: `OnboardingBasicsEvidenceTests` still carries its own hosting controller, window, run-loop pump and accessibility lookup, captures at `format.scale = 2` against `HostedSurface.captureScale`'s 3, and resolves `REPTODAY_EVIDENCE_DIR` verbatim with no story folder appended - the one layout divergence the resolver rule exists to prevent. Adopting the shared seams there is owed work, recorded with its full scope under "Owed work" in `docs/implementation-log.md`; write new suites against the rules, not against the exception.
Read `AccessibilityTree.labels(in:)` as "what is written down" and `spokenStrings(in:)` as "what VoiceOver actually says" - the latter counts labels **and** hints together, which is the only way an assertion can catch a sentence that appears once but is announced twice.
Two more shared test seams exist for the same don't-roll-your-own reason: `DefaultsSnapshot.swift`'s `restoreAfterTest(_:in:)` for the few unit tests that must write `UserDefaults.standard` (the telemetry gate is bound to it, so a private suite would prove nothing) and would otherwise leak the key into every later test in the process, and `RepTodayUITests/HealthAccessPrompt.swift`'s `answerHealthAccessSheetIfPresented(in:)`, now a precondition for any XCUITest that reaches the main tabs, since they raise the Health share prompt on arrival.

`convex/` is a second, unrelated toolchain and no iOS command touches it: `npm install` once, then `npm run typecheck` (`tsc --noEmit` over `convex/`, against the committed `convex/_generated/`, so it needs no deployment) and `npx convex dev --once` to deploy to your own dev deployment.

`npm test` (`vitest` + `convex-test`, added by US-T04) is the behavioural gate over the `POST /logEvent` boundary: it runs the real functions in process against an in-memory database and no deployment, so it needs neither network nor `.env.local`. `convex/README.md` records what the suite covers and the one write-time residual it cannot reach.

**CI:** `.github/workflows/ci.yml` gates every PR into `main` (and pushes to it) on both toolchains in parallel jobs - `sink` (ubuntu: `npm ci` + `npm run typecheck` + `npm run test`) and `ios` (macos-15, Xcode 16.4, iPhone 16 / iOS 18.5 simulator). The iOS job `xcodegen generate`s then builds and **runs the `RepToday` unit suite** (the gate) and **build-for-testing-only** compiles the `RepTodayUITests` scheme (XCUITests are compile-checked, not run, since they launch the app out of process and are slow/flaky on a hosted runner - run them locally when the touch path is in question). It needs no secrets: the app's CloudKit/HealthKit/Sign in with Apple entitlements make a fully unsigned build (`CODE_SIGNING_ALLOWED=NO`) crash the app-hosted test runner, so CI uses cert-less ad-hoc signing (`CODE_SIGN_IDENTITY=-`, team/profile cleared) which loads entitlements on the simulator without any certificate. No new third-party package is added (Lottie stays the app's only dependency; xcodegen is a build-time generator). The local `no-mistakes` pipeline is unchanged and still runs the same `xcodebuild test`.

## Architecture

**Monorepo:** `ios/` is the whole MVP; `convex/` is the telemetry sink only - one append-only `events` table, one internal `logEvent` mutation, and one `POST /logEvent` HTTP action (US-T03, hardened by US-T04, abuse-guarded by US-T14) that is the sink's single entry point, deliberately dumb with no analysis in it, and now reachable by the shipped client though nothing in the app calls it yet; US-T14 also adds a second, ephemeral `rateLimits` helper table (its only non-`events` table) plus `convex/rateLimit.ts` and a maintenance cron (`convex/crons.ts`) - a throttle store, not an evidence surface (see the Source of Truth note above and `convex/README.md`). There is still **no backend behind the core loop**, which stays fully on-device and offline. Standard Convex layout, so the npm project (`package.json`) sits at the repo root and the functions in `convex/` - see `convex/README.md`. `proxy/` is a deploy-ready but unwired Cloudflare Worker for the deferred Phase-2 LLM slices (holds the Anthropic key, stores nothing), now serving **two** stateless routes selected by pathname: `POST /variety-language` (US-N05, receives only two pillar values) and `POST /coach` (US-AC01, receives only the app-audited non-identifying `CoachContextBundle` plus the user's message); it has its own JS/ESM dev-only test toolchain (`vitest` + `tsc --checkJs`, `npm run typecheck`/`npm test` from `proxy/`) - see `proxy/README.md`.

**MVVM + protocol-based services.** Views read services from `@Environment(\.services)`; ViewModels are `@Observable`; services are protocols in `Services/Protocols/` with mock and real implementations; `DI/ServiceContainer.swift` wires them (`mock()` for tests/previews, `live(context:installId:analyticsGate:analyticsService:)` for the app, whose two optional trailing parameters carry the telemetry consent gate and let a test substitute the telemetry sink), so swapping in a real implementation is a one-line change.

**Persistence:** CoreData over `NSPersistentCloudKitContainer` with two stores - the **Cloud** configuration (`CDUser`, `CDWorkoutLog`, `CDSessionPolicy`) mirrors to the user's private iCloud database, and the **Local** configuration (`CDActiveSession`) is device-bound transient state that never syncs. The core loop works fully offline and with no iCloud account; sync is additive and falls back to local-only on any CloudKit failure. Domain models are plain `Codable` structs; nested fields persist as JSON-encoded `Data`.

**Integrations & navigation:** Sign in with Apple, CloudKit, write-only HealthKit, and StoreKit 2 (free unlimited core, premium depth only) never gate the core loop and degrade quietly; `AppState` (`@Observable`, UserDefaults-persisted) controls onboarding vs. main tabs, the selected tab, and the telemetry opt-out flag. The Profile tab is still mostly the placeholder it has always been, with two real destinations on it: a premium-gated `Coach` row (`Views/Coach/CoachEntryRow.swift`, US-AC03) whose `CoachGateViewModel` entitlement read sends a Premium subscriber into `Views/Coach/CoachView.swift` (US-AC02, the talking AI coach) and opens the paywall (`PaywallView(entryPoint: .coachUpsell)`) for a free user, and `Views/Settings/SettingsView.swift`, a sectioned Settings screen with a Privacy section (telemetry opt-out), a separate **AI Coach** privacy section mirroring the coach data disclosure (US-AC04, footer copy from `CoachDataDisclosureCopy`, touching neither the telemetry flag nor its footer), a **Training safety** section linking to the injury control (US-AC08, `Views/Settings/InjuryFlagsView.swift` - the one place `UserProfile.injuries` is set or cleared after onboarding, and the destination the coach's routing offer navigates to), and a destructive **Account** section (US-AD01, the mandatory App Store 5.1.1(v) account-deletion path) - a later Profile story extends it with another `Section` rather than replacing it. Account deletion (`Services/Account/AccountDeletionService.swift`, orchestrated once from `AccountDeletionViewModel` behind an `isDeleting` re-entrancy guard) tears down every store in a fixed order - the CloudKit-mirrored Cloud records via `deleteCurrentUser()` + the wholesale, user-id-free bulk deletes `WorkoutLogServiceProtocol.deleteAllLogs()`/`SessionPolicyStore.deleteAll()`, the device-local `CDActiveSession` via `ActiveSessionStore.clearAll()`, then the reinstall-surviving Keychain identifier via `AuthServiceProtocol.signOut()` - then resets `AppState` to route back to onboarding; it is idempotent and safe for the local-UUID (never-signed-in-with-Apple) user. So the wire contract has both ends and the wire, and no caller. The **identity** those events carry landed separately in US-T05, on `AppState` (`Utilities/AppState.swift`): `installId` is a random UUIDv4 minted on first launch and held only in `UserDefaults`, alongside `firstLaunchAt`, a `lastActiveAt` that only `init` writes (so it moves on a cold launch, not on a resume, and nothing reads it), and a computed `installWeek` that calls `ConsistencyScore.startOfWeek(_:_:)` rather than re-deriving a week boundary. Where it is *not* kept is the load-bearing part: never the Keychain, the IDFA, `identifierForVendor`, the Sign in with Apple identifier, or an email, because an id that outlives an uninstall resurrects an identity the user believed they deleted - though `UserDefaults` buys "dies with the app **absent a backup restore**" rather than an absolute, since `Library/Preferences` rides iCloud/iTunes backups and device-to-device transfer. `AppState.init` therefore takes injected `now`/`calendar`/`newInstallId` seams, and a reinstall is modelled in tests as a wiped `UserDefaults` suite. The id reaches the transport by being **passed down**, not re-read: `RepTodayApp.init()` builds `AppState` first and hands `installId` to `ServiceContainer.live(context:installId:)`, so a second code path can never disagree with `AppState` about which of the three launch states an install is in. Three launch states are resolved at construction and stay stable across relaunches: a genuine first launch mints the id and stamps `firstLaunchAt`; an install that already existed when this build shipped - discriminated as **onboarded with no stored `installId`** - mints an id but is *not* a first launch and, absent an origin already on disk, gets `firstLaunchAt == nil` plus a persisted `firstLaunchUnknown` marker, so it neither fabricates an origin nor re-mints on every launch (accepted residual: an earlier build whose user never finished onboarding still reads as fresh); a stored id with neither an origin nor that marker is corrupt and re-mints whole. The rule is narrower than "re-mint the pair": a missing id is re-minted, a *usable stored origin is always kept* (`isFirstLaunch` is true only when this launch stamped the origin itself), and the `firstLaunchUnknown` marker records that no usable origin exists rather than that the pair was incomplete - discarding an origin that survived would cause the very miscohort the rule exists to prevent. So `firstLaunchAt` and `installWeek` are `Date?`, and US-T07 settled the **two** data-modelling decisions this left open, both falling out of one rule - `app_install` fires **iff `isFirstLaunch`**, return events only when `firstLaunchAt != nil` (see the US-T07 criteria in the funnel PRD for the recorded consequences). A `nil` cohort (an unknown-origin pre-existing install) emits **nothing** rather than the upgrade week - no `app_install`, no returns - so K4's denominator omits it (acceptable because that population is empty until the first public build). A re-minted identifier beside a surviving origin emits **no** `app_install` (keying off the origin stamp, not the mint, so one physical install is not double-counted) but *does* window its return events off that origin, leaving the id in K4's numerator and absent from its denominator. `install_week`'s wire form was also decided here: a coarse `yyyy-MM-dd` week-start string (`AppEntryTelemetry.installWeekString`), never a precise timestamp. The re-minted state stays unreachable today (nothing clears `installId` alone), so the constraint that held US-T06 back from a "reset telemetry identity" control still binds any later story that would add one - it must not resurrect that state without re-confirming this decision. `installWeek` is bucketed in `AppState.cohortCalendar` (Gregorian, Sunday-start, `America/Los_Angeles`) and not `Calendar.current`, because it is grouped across users server-side; the on-device Consistency Score stays on `Calendar.current` on purpose, since a training week is a local week - change the constant, not the score. The two calendars are coupled, and US-T11 settled the seam: `week_active` carries no properties, so the server can only bucket it by client timestamp, and its cadence buckets in `AppState.cohortCalendar` rather than inheriting `Calendar.current` from the `ProgressAnalytics` rollup whose `ConsistencyScore.startOfWeek` bucketing it reuses - the same cross-user split, for the same reason. Change one calendar only with the other. `previousActiveAt` snapshots the `lastActiveAt` the previous cold launch left, because `init` overwrites it before anything can read it; nothing reads the snapshot today, and it is **not** what the day-7/day-30 return windows measure from (those are `firstLaunchAt`).

## The Deterministic Engine

Pure Swift, on-device, no network, no LLM, <100ms. Step 0 overrides (cold start, Return) run first and are no-ops in the steady state; the cold start also carries a **Start Seed** - a difficulty band `[startingDifficultyFloor, cappedMaxDifficulty]` over strength/primal plus a volume seed, both seeded from `profile.fitnessLevel`, eased a tier per `tooHard` rating, and retired at the handoff (which records the floor the week actually ran at so Step 5 does not treat a withheld chain as fresh).

1. **Session shape** - 5-10 single-focus; 11-20 blend light; 21-40 blend full; 41-60 blend extended.
2. **Pillar balance** - **every** session is **strength-led**, structurally (US-001/US-002, made unconditional by **US-M01**). There is no strength-vs-mobility split step anymore: `PillarBalance`/`PillarWeights` were **removed** by US-M01, and `SessionAssembly` builds the training middle as a single strength block (primal folded in) for single-focus and the shorter blends, or a strength block plus a dedicated primal block for an extended (41-60 min) blend - **never a mobility middle block at any length**. Mobility survives only as the warm-up and cooldown bookends, which since **US-M02** are *pattern-matched*: each mobility movement carries a `complements: [MovementPattern]` tag (`Exercises.json`, load-validated), and both bookends **lead** with a stretch complementing the day's lead strength pattern, then fill with the existing staleness / no-repeat ordering - a preference, never a filter (`SessionAssembly.leadingComplement`/`leadStrengthPattern`), with the general pool as the never-starved fallback. The minutes the retired **Movement Practice** mobility block used to hold were reallocated to strength (US-M01 decision 3), so a blend's training time is essentially all strength (short/full) or strength leading a small primal minority (extended, `SessionAssembly.extendedPrimalTrainingShare = 0.15`, strength >~0.80 of training). Since **US-M03** the desk-worker `sitsLong` signal *biases* bookend selection (never a direct sizing lever): it stable-promotes posture/hip openers - stretches whose `complements` name a hip-dominant pattern (`SessionAssembly.postureHipPatterns` = squat/hinge) - to the front of the warm-up/cooldown pools, *underneath* the US-M02 lead-complement promotion, a reorder-only preference that changes no block's count and no bookend stretch count so it can never re-inflate a short session or reintroduce a mobility middle block (`SessionAssembly.postureHipLean`/`isPostureHipOpener`); it does change which stretches *fill* the fixed-count bookends, and since stretches differ in `workSecondsPerSet` a desk worker's bookend duration - and, through the timing fit that feeds `trainingBudget`, a strength set count - can differ; since **US-CC08** paced rep-based stretches up while leaving hold stretches alone, that is no longer even incidental (a desk worker's 45-min warm-up costs ~32s more, which the fit pays out of a strength round), so round counts legitimately differ across profiles. What is test-guarded at the shipped catalog/lengths (`SitsLongBookendBiasTests.testSitsLongChangesNoTrainingMovementOrTarget`) is the real invariant rather than byte-identity: the training middle holds the same movements at the same per-set targets, every block stays internally even, no mobility middle block appears, and equal bookend seconds still produce identical round counts - so the bias can reach the training middle through no channel but bookend cost. `pillarWeighting` is likewise inert (see `SessionPolicy`). Primal is untouched (folded into strength short, its own block at 41-60 min).
3. **Movement-pattern focus** - stalest-first; never repeat the previous session's lead pattern.
4. **Filter pool** - drop by phase, injuries, difficulty cap, recent skips; everything is bodyweight (Zero-Equipment Floor). The difficulty cap is the *effective* cap (`ExercisePoolFilter.effectiveDifficultyCap`): the `FitnessLevel` band while `.discipline`, lifted to the full `1...5` catalog once the user has earned the `.strength` phase (US-SP01).
5. **Progression-chain selection** - the user's frontier tier, advancing only when criteria are cleared; avoid the last `varietyWindow` sessions (default 3).
6. **Adaptive Overload** - capacity-relative reps/sets/holds, never a fixed heroic number; the Asymmetric Ramp backs off fast and climbs slow, paced by `progressionRate`.
7. **Assemble + fit timing (even-round circuit model, US-CC03/US-CC04, ADR-0003)** - warm-up first, cooldown over 10 min, land within +/-1 min of the request. A training block is played as circuit **rounds**: every exercise in it carries the **same** set count = the block's round count (the strength block and the extended 41-60 min dedicated primal block are each internally uniform), so the block is genuinely even and "Round N of M" is well-defined. The planned wall-clock (`SessionAssembly.blockSeconds`, summed by `plannedSeconds`/`totalSeconds` plus one between-block transition) prices a circuit block as `rounds × Σ workPerSet + rounds × between-station transitions + (rounds - 1) × round-rest`; a bookend is one set each, linear. `SessionAssembly.workSecondsPerSet` prices a set as a fixed setup cost plus the per-unit work of the target prescribed (a hold's per-unit cost is one second per prescribed second *per side*, via `Exercise.isPerSide`/`sidesPerSet`), so a grown or seeded target is planned honestly, then scales the rep half by `workPaceGenerosityFactor` (US-CC08) so the number is a **generous runtime pace** rather than a typical-case estimate. Since US-CC01 the player's auto-advancing work window counts down this very number, so it is one source of truth for planning and runtime both; it is still never *measured* (a set logs the target it was prescribed), so systematic bias matters and per-second precision does not. **Two rest gaps** (US-CC04): a fixed ~15s **between-station transition** (`transitionSeconds`, the "Next: get ready" beat) inside a round, and a bounded **between-round rest** (`minRoundRestSeconds`...`maxRoundRestSeconds`, 30-75s) that the fit tunes as its **primary lever** - the retired per-exercise `.addSet`/`.removeSet` moves are gone. The fit is a deterministic greedy over a combined `setRoundsAndRest` move (round count + in-band rest tuned together so it can trade a round for rest in one step) plus whole-exercise promote/drop at the block's round count - never touching Step 6's capacity-relative per-set target and never making a block uneven. The strength/primal round-count rail is `maxTrainingSets`, capped at **4** by US-RC01 (`minTrainingSets` 2; was `1...8`): no exercise is ever prescribed more than four times, and once every active station sits at the cap the fit fills the rest of a long session **wider** instead - promoting a further progression chain per pattern as an accessory (`ProgressionChainSelection.selectAll`, `Builder.strengthBlock`/`primalBlock`) depth-first from the reserve via the coupled `.addReserveWithRounds` move (round count solved jointly with adding the station, see the Fourth PRD note above). The warm-up/cooldown bookends stay one set per exercise (`allowSetAdjust: false`) and grow only by promoting more distinct movement *types*; the warm-up is seeded directly at a length-scaled count (`SessionAssembly.warmupExerciseCount`: ≤10 min 1, 11-20 2, 21-40 3, 41-60 4, all active items with `minItems` pinned), a lean opening (US-003), capped by the `maxWarmupExercises` ceiling (4). (In-session swap keeps the block's round count - it never re-picks a slot's set count - so a swap can never make a circuit uneven; it also holds across all remaining rounds and the block stays even, US-CC07.)

In-session **swap** substitutes within the same pillar, pattern, difficulty band, and time budget, sized by the session's own policy (`progressionRate`, Start Seed, `varietyWindow`, Return/re-entry ease). Under the even-round model (US-CC03) it **keeps the slot's set count** - which on a training block is the block's uniform round count - so a swap can never make a circuit uneven; the per-slot set-count re-pick lever is retired (a substitute joins the circuit at the block's round count or declines), and the widened work-scaled `slotTolerance` now applies to every slot since none has a set lever. A swap therefore moves the session by at most the swapped slot's tolerance. Applying a swap across all remaining rounds landed in US-CC07 (player-side: replacing the one `Step` per station carries the substitute through every remaining round with the circuit staying even; the substitute is an honest late entrant, logging only the rounds it played); reshaping the block's shared round-rest on swap to re-absorb the in-tolerance drift was scoped out of US-CC07 (bounded already by `slotTolerance`). A deterministic on-device **AI Programmer** (`Services/Programmer/`) writes the per-user `SessionPolicy` the engine reads: it detects re-program triggers, diagnoses plateaus, learns the Default Duration, and never returns a workout. Since US-AC07 the policy has a **second writer** - the premium AI coach (`Services/Coach/CoachSessionPolicyService`) - which may only nudge the three preference levers as a safety-sovereign overlay onto the Programmer's freshest policy, never clobbering a safety move (ADR-0005, and the `CONTEXT.md` "Two-Writer Policy Safety" term).

## Consistency & Phase (no gamification)

No XP, no levels, no badges, no streak to break.

- **Consistency Score** - `weeklyAdherence = min(1, workoutsCompleted / weeklyGoal)`, a recency-weighted rolling average x 100. A 5-min session is a full show-up; a miss dents but never zeroes; a Return excuses the gap weeks it closed. `longestChain` is an all-time maximum surfaced as earned pride.
- **PhaseEvaluator** - deterministic, never user-selectable; Strength requires both sustained consistency and cleared entry tiers across push/squat/hinge/core. Earning Strength lifts the engine's effective difficulty cap to the full catalog (US-SP01, `ExercisePoolFilter.effectiveDifficultyCap`), so competence overrides the conservative onboarding fitness-level estimate.
- All copy is identity-framed ("you're someone who moves"), never loss-framed.

## Key Conventions

- `@Observable` only, never `ObservableObject`/`@Published`. All service methods are `async throws` - the one exception is `AnalyticsServiceProtocol.record(_:)`, which is `async` but not `throws` because emission is strictly fire-and-forget, so a call site reads `await analytics.record(event)` with no `try`.
- Enums are `Codable`, `CaseIterable`, and `Identifiable` where they have a stable id.
- Always use `Theme.Colors` / `Theme.Typography` / `Theme.Spacing`; never hardcode colors, fonts, or spacing.
- Button height 56pt, card radius 16pt, touch targets 44pt (60pt on active workout screens).
- Exercise library: 76 bodyweight movements in `Resources/Exercises.json`, all `equipment == []`, load-time-validated (26 of them mobility, each carrying a `complements: [MovementPattern]` bookend-matching tag since US-M02 - a missing tag on a mobility movement fails load).
- Accessibility throughout: VoiceOver, Dynamic Type, Reduce Motion, haptics with an audio alternative. Prescription copy has one source - `ActiveSessionView.targetText` (seen: "3 × 0:30 per side") and `.targetAccessibilityText` (spoken: nouns agreeing with their own counts, "1 set of a 45 second hold"); every other surface calls them instead of re-formatting.
- Pure engine/evaluator logic takes an injected `asOf` clock; never read the wall clock inside it.
- Tests live in `ios/RepToday/RepTodayTests/` (`XCTestCase` + `@testable import RepToday`); all new logic needs tests, and each story adds a row to `docs/test-coverage.md`. `ios/RepToday/RepTodayUITests/` is the XCUITest bundle under its own scheme, for the few things only a real touch can exercise.

## Out of Scope (MVP Non-Goals)

No LLM/AI calls in the loop, no custom backend behind the core loop (the telemetry sink is the one server-side thing that exists, and nothing in the loop reads it), no XP/levels/badges, no social/leaderboards/challenges, no equipment-based exercises, no full Strength-Phase catalog, no Android/widgets/Live Activities/Apple Watch (see the PRD's Non-Goals for the full list).

## Artifact Locations

PRDs and task briefs live in `.claude/agent/tasks/`; work products go under `artifacts/` - `reports/` (engineering, QA, test results), `specs/`, `learning-logs/` - created on demand.
