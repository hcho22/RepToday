## Project Overview

Rep Today is a discipline-first micro-workout iOS app (5-60 min sessions) for busy, desk-bound adults.
The user says how many minutes they have, and a deterministic on-device engine generates a complete zero-equipment session blending bodyweight strength and mobility - no browsing, no choosing, no thinking.
Strength is earned, not the entry promise: every user starts in the **Discipline Phase** and earns the **Strength Phase** through sustained consistency plus demonstrated competence, so all MVP users resolve to Discipline with the `PhaseEvaluator` already in place.
The MVP is Apple-native with no custom backend behind the core loop (the `convex/` telemetry sink is beside it, not under it); AI/LLM features are deferred to Phase 2, do language only, and never generate or adapt a workout.

## Build & Run

```bash
cd ios/RepToday && xcodegen generate    # regenerate the project from project.yml
xcodebuild -project ios/RepToday/RepToday.xcodeproj -scheme RepToday \
  -sdk iphonesimulator -configuration Debug \
  -destination 'generic/platform=iOS Simulator' build
xcodebuild -project ios/RepToday/RepToday.xcodeproj -scheme RepToday \
  -destination 'platform=iOS Simulator,name=iPhone 16' test
xcodebuild -project ios/RepToday/RepToday.xcodeproj -scheme RepTodayUITests \
  -destination 'platform=iOS Simulator,name=iPhone 16' test    # XCUITest suite, run on demand
```

The `RepToday` scheme builds the app and runs `RepTodayTests` - that is the default run, and everything except the XCUITests lives in it; if the destination will not resolve, use `xcrun simctl list devices available` and pass `-destination 'id=<UDID>'`.
Target iOS 17.0+, Swift 5.9, Xcode 16.3, bundle id `com.reptoday.app`.
`RepTodayUITests` is a second scheme on purpose: it installs and launches the app in a booted Simulator and drives it out of process, so folding it into `RepToday` would make every unit run wait on an app launch and inherit its failure modes.
Run it when the touch path is what is in question - it is the only place a production control is actually pressed rather than hosted.
`DEVELOPMENT_TEAM` is set to the signing team, so entitlement-gated paths (Sign in with Apple, CloudKit sync, HealthKit writes, live purchases) build for device; they still verify only on real hardware, never in the Simulator.
Historical device notes in `docs/implementation-log.md` and the PRDs predate this and describe the team as empty - read them as point-in-time records.
The evidence suites (`PerSideSwapEvidenceTests`, `OnboardingBasicsEvidenceTests`, `ProgressTabSnapshotTests`) render production screens to PNGs on every run, and `OnboardingImperialUITests` screenshots the running app the same way, but a plain `test` writes them to a per-run temporary directory so the worktree stays clean; append `REPTODAY_WRITE_EVIDENCE=1` (a build setting, since a Simulator-hosted test bundle inherits no shell environment - both schemes forward it) to regenerate the committed images under `artifacts/reports/<story>/`, or `REPTODAY_EVIDENCE_DIR=<root>` to send them elsewhere.
A suite never rolls its own path: `EvidenceOutput.directory(for:)` is the one resolver, and `REPTODAY_EVIDENCE_DIR` names a **root** with the story folder appended - never the final directory - so one redirected run keeps the same `<root>/<story>/<file>` shape as the committed baselines instead of scattering suites' renders into different layouts.
The XCUITest screenshots are produced on demand rather than committed: the suite always files them with its `.xcresult` too, so the two variables only decide where a second, browsable copy lands.
Hosting a production surface to capture or read it likewise goes through `HostedSurface.host(_:size:)` and `AccessibilityTree`, so every suite gets the same run-loop settling rather than an ad-hoc copy that reads a half-drawn screen.

`convex/` is a second, unrelated toolchain and no iOS command touches it: `npm install` once, then `npm run typecheck` (`tsc --noEmit` over `convex/`, against the committed `convex/_generated/`, so it needs no deployment) and `npx convex dev --once` to deploy to your own dev deployment.
There are two tsconfigs on purpose: `convex/tsconfig.json` is what the Convex CLI typechecks on every deploy, so it excludes `**/*.test.ts` and names no `types` array (naming one would switch off automatic `@types` inclusion for the deployed functions), and `convex/tsconfig.test.json` extends it with the test files plus the `vite/client` types; `npm run typecheck` runs both, so a deploy never depends on the test toolchain being installed while the suite stays typechecked.
`npm test` (`vitest` + `convex-test`, added by US-T04) is the behavioural gate over the `POST /logEvent` boundary: it runs the real functions in process against an in-memory database and no deployment, so it needs neither network nor `.env.local`. This repo has no CI, so both commands only run when someone runs them; `convex/README.md` records what the suite covers and the one write-time residual it cannot reach.

## Architecture

**Monorepo:** `ios/` is the whole MVP; `convex/` is the telemetry sink only - one append-only `events` table, one internal `logEvent` mutation, and one `POST /logEvent` HTTP action (US-T03, hardened by US-T04) that is the sink's single entry point, deliberately dumb with no analysis in it, and now reachable by the shipped client though nothing in the app calls it yet; there is still **no backend behind the core loop**, which stays fully on-device and offline. Standard Convex layout, so the npm project (`package.json`) sits at the repo root and the functions in `convex/` - see `convex/README.md`. `proxy/` is a deploy-ready but unwired Cloudflare Worker for the deferred Variety Language LLM slice (holds the Anthropic key, stores nothing, receives only two pillar values).

**MVVM + protocol-based services.** Views read services from `@Environment(\.services)`; ViewModels are `@Observable`; services are protocols in `Services/Protocols/` with mock and real implementations; `DI/ServiceContainer.swift` wires them (`mock()` for tests/previews, `live(context:installId:analyticsGate:analyticsService:)` for the app, whose two optional trailing parameters carry the telemetry consent gate and let a test substitute the telemetry sink), so swapping in a real implementation is a one-line change.

**Persistence:** CoreData over `NSPersistentCloudKitContainer` with two stores - the **Cloud** configuration (`CDUser`, `CDWorkoutLog`, `CDSessionPolicy`) mirrors to the user's private iCloud database, and the **Local** configuration (`CDActiveSession`) is device-bound transient state that never syncs. The core loop works fully offline and with no iCloud account; sync is additive and falls back to local-only on any CloudKit failure. Domain models are plain `Codable` structs; nested fields persist as JSON-encoded `Data`.

**Integrations & navigation:** Sign in with Apple, CloudKit, write-only HealthKit, and StoreKit 2 (free unlimited core, premium depth only) never gate the core loop and degrade quietly; `AppState` (`@Observable`, UserDefaults-persisted) controls onboarding vs. main tabs, the selected tab, and the telemetry opt-out flag. The Profile tab is still the placeholder it has always been, with one real destination on it: `Views/Settings/SettingsView.swift`, a sectioned Settings screen whose only section today is Privacy - a later Profile story extends it with another `Section` rather than replacing it.

**Anonymous product telemetry (funnel instrumentation, a separate PRD):** `AnalyticsServiceProtocol.record(_:)` takes an `AnalyticsEvent` - one of exactly 13 pre-registered event names (`gtm/06-channels/event-metric-schema.md`, snake_case raw values that are the wire contract), a millisecond client timestamp, and a non-identifying `[String: AnalyticsValue]` bag. US-T02 built the seam, US-T04 the **transport** behind it, and US-T06 the **consent** in front of it: `mock()` wires the recording in-memory `MockAnalyticsService`, while `live(context:installId:)` wires `LiveAnalyticsService` (`Services/Analytics/`), one fire-and-forget `URLSession` POST per event to the deployment's `POST /logEvent`, with no Convex SDK. **Nothing calls `record(_:)`**, so a shipping build carries a working pipeline that never fires; the 13 emission sites are US-T07 through US-T12. `record(_:)` checks an injected `isEnabled` gate - production passes the `AppState` instance's own `analyticsGate`, read per emission rather than captured, so the toggle takes effect on the next event and not the next launch - then hands the event to a detached task and returns - so no caller ever waits on the network, and every failure is swallowed. The wire body is a **second** encoding, `AnalyticsWireBody`: `{name, installId, clientTs, props}` with `props` flattened to plain scalars and `clientTs` a bare JSON number, deliberately *not* `AnalyticsEvent`'s own tagged `Codable` form, which stays tagged so `Int`/`Double` round-trip in process. The deployment origin is `Info.plist` configuration (`RepTodayAnalyticsEndpoint`), expanded from the **per-configuration** `REPTODAY_ANALYTICS_ENDPOINT` build setting in `ios/RepToday/project.yml`: Debug carries the dev deployment `courteous-dogfish-560`, Release carries **nothing**, because no production one is chosen yet. A missing, empty, or unusable value makes the build **inert, never fatal** - `LiveAnalyticsService.configured(...)` returns `nil` and the container falls back to `NoOpAnalyticsService` - so a Release build silently sends no data rather than silently sending to the wrong destination, and choosing plus configuring the production deployment is a precondition for shipping any build that emits (US-T07 onward). That split is asserted against the running app bundle in `LiveAnalyticsServiceTests`, each half compiled only into the configuration that can observe it - but only the Debug half ever runs, because `ENABLE_TESTABILITY` is Debug-only here so `@testable import` cannot resolve under `-configuration Release`; the Release half is verified at the built artifact instead (`plutil -extract RepTodayAnalyticsEndpoint` on `Release-iphonesimulator/RepToday.app/Info.plist`). `live(context:installId:analyticsGate:analyticsService:)` also takes the sink, defaulting to exactly that resolution, so a test building the production container for its CoreData services substitutes an inert one and is structurally unable to reach the wire once the emission sites land - rather than unable only because none exist yet (FR-13). That seam is **in-process only**: `RepTodayUITests` launches the real app, which builds its own container, so the only gate reachable there is `isEnabled`. **US-T06 closed that half.** The consent flag is `AppState.analyticsEnabled` (default on, with absence resolved as on by `AppState.isAnalyticsEnabled(in:)` - a plain `bool(forKey:)` would read a never-written key as opted *out*), turned off from `SettingsView` (the toggle, with the explanation as the Privacy section's footer so VoiceOver reads it once rather than once as body copy and again as the toggle's hint), disclosed on the first onboarding screen, and overridable out of process as `-AppState.analyticsEnabled NO`, because `UserDefaults` reads the argument domain first - the only mechanism an out-of-process suite has, though it is available rather than universally applied: `OnboardingImperialUITests` passes it on every launch, while `TelemetryOptOutUITests` passes it only where being opted out is the assertion (its opted-in legs are held off the wire by the probe harness's in-process interceptor instead, and its screenshot leg by neither - harmless only while nothing emits, so US-T07 has to revisit it). The gate travels the same way `installId` does - `RepTodayApp.init()` hands `appState.analyticsGate` to `live(...)`, so the reader is bound to the store `AppState` writes rather than both sides independently naming `.standard`; production still resolves to `.standard`, which is what puts `NSArgumentDomain` in front of the persisted value, so moving `AppState` onto an app-group suite later is a change that has to re-verify the override first (noted on `AppState.init`'s `userDefaults` parameter). The gate is proved out of process by `RepTodayUITests/TelemetryOptOutUITests` against `Services/Analytics/TelemetryUITestHarness.swift`, a `#if DEBUG` and launch-argument-gated probe supplying the two things the shipping app cannot - an emission attempt (no call site exists yet) and a count another process can read - so the assertion observes the gate rather than the absence of anything to emit; it carries a positive control, and its non-vacuity was checked by sabotaging the gate and watching it fail. What it proves stops at the `URLProtocol` boundary inside the app, which is what keeps FR-13 (no bytes leave); that bytes reach Convex at all is the live, non-re-running transcript `artifacts/reports/US-T06/validation.md`. The **sink** that POST targets: US-T03 deployed `convex/`'s `events` table, `logEvent` mutation, and `POST /logEvent` -> `204` HTTP action, which rejects an unknown event name, an oversized property bag, and a missing or wrong-kind `installId`/`clientTs` (presence and kind only - those are the two columns K4 and K1 are counted from, so coercing them would land `"undefined"`/`NaN` rows that look valid), and does nothing else; a caller's fault answers `400` with the message, the sink's own failure `5xx` with no detail - which is why the action runs the SDK's `convexToJson` over the arguments itself, so a `props` field name Convex refuses lands on the caller's side of that split instead of looking like an outage. US-T04 added the two size caps US-T03 had knowingly left off, once a real client existed to need them: `installId` bounded at 64 UTF-8 bytes (length only, never format) and the request body at 64 KiB, checked before anything is parsed so an oversized payload can no longer reach argument serialization and answer `5xx`. It also added the boundary's first re-runnable test (`convex/http.test.ts`, `npm test`). The split is still not total, and `convex/README.md` records the residual in full: a caller fault that only a *write-time* Convex rule catches - `props` nested past the value-depth limit - still surfaces as `5xx`. Those checks are only worth anything because the action is the sink's one way in: `logEvent` is an `internalMutation`, so a new writer belongs behind the action rather than beside it - a public Convex function is callable directly on the deployment's `.convex.cloud` API and would skip all of them. So the wire contract has both ends and the wire, and no caller. The **identity** those events carry landed separately in US-T05, on `AppState` (`Utilities/AppState.swift`): `installId` is a random UUIDv4 minted on first launch and held only in `UserDefaults`, alongside `firstLaunchAt`, a `lastActiveAt` that only `init` writes (so it moves on a cold launch, not on a resume, and nothing reads it), and a computed `installWeek` that calls `ConsistencyScore.startOfWeek(_:_:)` rather than re-deriving a week boundary. Where it is *not* kept is the load-bearing part: never the Keychain, the IDFA, `identifierForVendor`, the Sign in with Apple identifier, or an email, because an id that outlives an uninstall resurrects an identity the user believed they deleted - though `UserDefaults` buys "dies with the app **absent a backup restore**" rather than an absolute, since `Library/Preferences` rides iCloud/iTunes backups and device-to-device transfer. `AppState.init` therefore takes injected `now`/`calendar`/`newInstallId` seams, and a reinstall is modelled in tests as a wiped `UserDefaults` suite. The id reaches the transport by being **passed down**, not re-read: `RepTodayApp.init()` builds `AppState` first and hands `installId` to `ServiceContainer.live(context:installId:)`, so a second code path can never disagree with `AppState` about which of the three launch states an install is in. Three launch states are resolved at construction and stay stable across relaunches: a genuine first launch mints the id and stamps `firstLaunchAt`; an install that already existed when this build shipped - discriminated as **onboarded with no stored `installId`** - mints an id but is *not* a first launch and, absent an origin already on disk, gets `firstLaunchAt == nil` plus a persisted `firstLaunchUnknown` marker, so it neither fabricates an origin nor re-mints on every launch (accepted residual: an earlier build whose user never finished onboarding still reads as fresh); a stored id with neither an origin nor that marker is corrupt and re-mints whole. The rule is narrower than "re-mint the pair": a missing id is re-minted, a *usable stored origin is always kept* (`isFirstLaunch` is true only when this launch stamped the origin itself), and the `firstLaunchUnknown` marker records that no usable origin exists rather than that the pair was incomplete - discarding an origin that survived would cause the very miscohort the rule exists to prevent. So `firstLaunchAt` and `installWeek` are `Date?`, and US-T07 carries **two** recorded decisions on its own acceptance criteria, not one: what a `nil` cohort emits rather than silently emitting the upgrade week, and - separately, because there a valid `install_week` *is* available - whether a re-minted identifier sitting beside a surviving origin emits `app_install` at all, since keying off the mint double-counts one physical install while keying off the origin stamp (today's behaviour) leaves an id active in K4's numerator and absent from its denominator. That second state is unreachable today, nothing clears `installId` alone, so US-T06 was told not to add a "reset telemetry identity" control until US-T07 has answered, and did not - its opt-out gates emission and leaves `installId` untouched, asserted rather than intended. The constraint still binds any later story. `installWeek` is bucketed in `AppState.cohortCalendar` (Gregorian, Sunday-start, `America/Los_Angeles`) and not `Calendar.current`, because it is grouped across users server-side; the on-device Consistency Score stays on `Calendar.current` on purpose, since a training week is a local week - change the constant, not the score. The two calendars are coupled from here on, and US-T11 owns the seam: `week_active` carries no properties, so the server can only bucket it by client timestamp, and that story has a criterion deciding which calendar its cadence uses rather than inheriting `Calendar.current` from the `ProgressAnalytics` rollup it reuses. `previousActiveAt` snapshots the `lastActiveAt` the previous cold launch left, because `init` overwrites it before anything can read it; nothing reads the snapshot today, and it is **not** what the day-7/day-30 return windows measure from (those are `firstLaunchAt`).

## The Deterministic Engine

Pure Swift, on-device, no network, no LLM, <100ms. Step 0 overrides (cold start, Return) run first and are no-ops in the steady state; the cold start also carries a **Start Seed** - a difficulty band `[startingDifficultyFloor, cappedMaxDifficulty]` over strength/primal plus a volume seed, both seeded from `profile.fitnessLevel`, eased a tier per `tooHard` rating, and retired at the handoff (which records the floor the week actually ran at so Step 5 does not treat a withheld chain as fresh).

1. **Session shape** - 5-10 single-focus; 11-20 blend light; 21-40 blend full; 41-60 blend extended.
2. **Pillar balance** - stalest pillar by days-since-worked; mobility lean for desk workers; policy `pillarWeighting` scales it.
3. **Movement-pattern focus** - stalest-first; never repeat the previous session's lead pattern.
4. **Filter pool** - drop by phase, injuries, difficulty cap, recent skips; everything is bodyweight (Zero-Equipment Floor).
5. **Progression-chain selection** - the user's frontier tier, advancing only when criteria are cleared; avoid the last `varietyWindow` sessions (default 3).
6. **Adaptive Overload** - capacity-relative reps/sets/holds, never a fixed heroic number; the Asymmetric Ramp backs off fast and climbs slow, paced by `progressionRate`.
7. **Assemble + fit timing** - warm-up first, cooldown over 10 min, land within +/-1 min of the request. `SessionAssembly.workSecondsPerSet` prices a set as a fixed setup cost plus the per-unit work of the target prescribed (a hold's per-unit cost is one second per prescribed second *per side*, via `Exercise.isPerSide`/`sidesPerSet`), so a grown or seeded target is planned honestly; the work half is never timed at runtime, so this is a planning-only number where systematic bias matters and per-second precision does not.

In-session **swap** substitutes within the same pillar, pattern, difficulty band, and time budget, sized by the session's own policy (`progressionRate`, Start Seed, `varietyWindow`, Return/re-entry ease). It keeps the slot's set count whenever a peer fits at it and re-picks one inside `minTrainingSets...maxTrainingSets` only when nothing else would keep the session in its minutes - never on the single-set warm-up/cooldown bookends, which get a work-scaled tolerance instead. A deterministic on-device **AI Programmer** (`Services/Programmer/`) writes the per-user `SessionPolicy` the engine reads: it detects re-program triggers, diagnoses plateaus, learns the Default Duration, and never returns a workout.

## Consistency & Phase (no gamification)

No XP, no levels, no badges, no streak to break.

- **Consistency Score** - `weeklyAdherence = min(1, workoutsCompleted / weeklyGoal)`, a recency-weighted rolling average x 100. A 5-min session is a full show-up; a miss dents but never zeroes; a Return excuses the gap weeks it closed. `longestChain` is an all-time maximum surfaced as earned pride.
- **PhaseEvaluator** - deterministic, never user-selectable; Strength requires both sustained consistency and cleared entry tiers across push/squat/hinge/core.
- All copy is identity-framed ("you're someone who moves"), never loss-framed.

## Key Conventions

- `@Observable` only, never `ObservableObject`/`@Published`. All service methods are `async throws` - the one exception is `AnalyticsServiceProtocol.record(_:)`, which is `async` but not `throws` because emission is strictly fire-and-forget, so a call site reads `await analytics.record(event)` with no `try`.
- Enums are `Codable`, `CaseIterable`, and `Identifiable` where they have a stable id.
- Always use `Theme.Colors` / `Theme.Typography` / `Theme.Spacing`; never hardcode colors, fonts, or spacing.
- Button height 56pt, card radius 16pt, touch targets 44pt (60pt on active workout screens).
- Exercise library: 57 bodyweight movements in `Resources/Exercises.json`, all `equipment == []`, load-time-validated.
- Accessibility throughout: VoiceOver, Dynamic Type, Reduce Motion, haptics with an audio alternative. Prescription copy has one source - `ActiveSessionView.targetText` (seen: "3 × 0:30 per side") and `.targetAccessibilityText` (spoken: nouns agreeing with their own counts, "1 set of a 45 second hold"); every other surface calls them instead of re-formatting.
- Pure engine/evaluator logic takes an injected `asOf` clock; never read the wall clock inside it.
- Tests live in `ios/RepToday/RepTodayTests/` (`XCTestCase` + `@testable import RepToday`); all new logic needs tests, and each story adds a row to `docs/test-coverage.md`. `ios/RepToday/RepTodayUITests/` is the XCUITest bundle under its own scheme, for the few things only a real touch can exercise.

## Out of Scope (MVP Non-Goals)

No LLM/AI calls in the loop, no custom backend behind the core loop (the telemetry sink is the one server-side thing that exists, and nothing in the loop reads it), no XP/levels/badges, no social/leaderboards/challenges, no equipment-based exercises, no full Strength-Phase catalog, no Android/widgets/Live Activities/Apple Watch (see the PRD's Non-Goals for the full list).
